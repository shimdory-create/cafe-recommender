# 운영 런북 — 뭔가 이상할 때

이 서비스는 결제도 업데이트도 없이 도는 것을 전제로 만들었다. 그래도 언젠가는
멈춘다. 그때 **5분 안에 원인을 찾는 것**이 이 문서의 목적이다.

전제: 조작이 필요한 일은 거의 없다. 아래 표에서 증상을 찾아 그 줄만 읽으면 된다.

---

## 신호는 두 곳으로 온다

| 경로 | 언제 | 조건 |
|---|---|---|
| **GitHub 메일** ("daily-watch failed") | 이상이 생긴 날 아침 | PC 가 꺼져 있어도 온다 |
| **금요일 정오 카톡 마지막 줄** | 매주 금요일 | 이 PC 의 Claude Code 가 켜져 있어야 |

카톡 마지막 줄이 뜻하는 것:

| 줄 | 뜻 | 할 일 |
|---|---|---|
| `자동수집 정상` | 이상 없음 | 없음 |
| `주의: 판정 지연` | 무료 쿼터가 일찍 끊긴 정도 | 없음 (정상 범위) |
| `점검 필요: …` | 손봐야 한다 | 아래 표에서 찾는다 |
| **줄이 아예 없다** | 옛 버전이 돌았거나 발송 경로가 바뀜 | 아래 "카톡이 안 온다" |

## 증상별 대응

### 워크플로가 아예 안 돌았다

GitHub 무료 스케줄러는 혼잡하면 **예약을 조용히 버린다.** 실패가 아니라
실행 자체가 없어서 메일도 안 온다 (2026-08-24 에 classify·watch 가 그랬다).

하루 누락은 정상 범위다 — 다음 날 이어서 처리된다. 이틀 연속이면 감시가
`수집 멈춤` 으로 잡는다. 급하면 손으로 돌린다:

[Actions 탭](https://github.com/shimdory-create/cafe-recommender/actions) →
워크플로 선택 → **Run workflow**

### 목록이 며칠째 그대로다

```bash
npm run watch
```

`수집 멈춤` 이나 `수집 조기 중단` 이 나오면 워크플로가 안 돈 것이다.
[Actions 탭](https://github.com/shimdory-create/cafe-recommender/actions) 에서
빨간 X 를 열어 **실패한 단계 이름**을 확인한다. 지금까지 깨진 곳은 전부
마지막 `데이터 커밋` 단계였고, 규칙은 `scripts/commit-data.sh` 한 곳에 있다.

수동으로 한 번 돌리려면 Actions 탭 → 워크플로 선택 → **Run workflow**.

### `점검 필요: 판정 정체` — 신규 카페가 안 늘어난다

판정은 Gemini 무료 쿼터를 쓴다. **하루 한도까지 쓰고 멈추는 것은 정상**이고,
다음 날 이어서 처리한다. 그런데 **한 곳도 못 한 날이 이어지면** 남이 우리 키를
쓰고 있을 수 있다.

**2026-08-21 대화에 노출됐던 키는 2026-09-29에 교체 완료했다** — 지금 쓰는
키는 그 사건과 무관한 새 키다("Default Gemini Project" 안에 새로 발급,
프로젝트는 그대로라 healthcare-radar 와의 RPM 배분엔 영향 없음). 노출됐던
옛 키는 삭제하지 않고 그대로 뒀다 — 이미 안 쓰니 당장 위험하진 않지만,
언젠가 정리해도 된다(AI Studio → API 키 → "...0jCQ" "Gemini API Key").

혹시 또 이런 일이 필요해지면 같은 절차다 — [aistudio.google.com/apikey](https://aistudio.google.com/apikey)

1. **반드시 기존 "Default Gemini Project" 안에서 Create API key** (다른
   프로젝트를 새로 만들면 서비스 계정 바인딩이 강제돼 우리 코드의 단순 키
   인증이 안 통한다 — 2026-09-29 실측, 위 "속도제한 발생" 항목 참고)
2. `.env` 의 `GEMINI_API_KEY=` 교체
3. GitHub → Settings → Secrets and variables → Actions → `GEMINI_API_KEY` 수정
4. 바꾸고 나서 꼭 실제로 한 번 호출해본다 — 프로젝트를 잘못 고르면 키가
   발급은 되는데 호출은 401 로 실패한다(겉보기엔 멀쩡해 보여서 더 위험).

카카오 키도 같은 절차다 (카카오 개발자센터 → 내 애플리케이션 → 앱 키).

### `점검 필요`/`주의: 속도제한 발생` — 다른 프로젝트와 키를 나눠 쓰는 중

**2026-09-29 확인: 이 GEMINI_API_KEY 는 `healthcare-radar`라는 다른 프로젝트와
같은 Google Cloud 프로젝트(`gen-lang-client-0437601059`)를 공유한다.** 둘이
합쳐서 Gemini 무료 티어의 실제 한도(분당 15건, RPM)를 나눠 쓰는 구조라, 한쪽이
바빠지면 다른 쪽이 속도제한(429)을 맞을 수 있다.

**지금 합의된 배분**(`src/cli/context.ts` 의 `llmLimit` 주석 참고):
- healthcare-radar: 분당 7건
- 이 프로젝트(cafe-recommender): 분당 5건 — 합 12건, 15건 한도에 3건 여유

처음엔 9+6=15로 맞췄다가, 여유가 0이라 우연히 겹치는 순간을 못 막는다는
점이 걸려서 2026-09-29 같은 날 바로 이렇게 낮췄다. 이 배분은 **고정값이
아니라 합의**다. 어느 한쪽 물량이 늘어 이 몫이 자주 답답해지면(판정이
계속 느리다, 429가 잦다) 레이다 쪽과 다시 조율해야 한다. 실제로 429를
맞았을 때의 추가 완충(60초 쉬고 재시도)은 `classify.ts` 등의
`COOLDOWN_ON_QUOTA_ERROR_MS` 참고 — 이건 상대방과 무관하게 이쪽 코드만으로
작동한다.

**근본 해결(키를 프로젝트별로 완전히 분리)은 지금 막혀 있다** — 이 Google
계정에서 새로 만드는 프로젝트는 Gemini API 키를 서비스 계정에 바인딩하도록
강제해서, 우리 코드가 쓰는 단순 API 키 인증(`x-goog-api-key` 헤더)이 안
통한다. 분리하려면 OAuth2/서비스 계정 인증을 새로 구현해야 하는데 — 범위가
커서 보류 중이다. 필요해지면 `src/llm/gemini.ts` 부터 다시 설계한다.

**감시**: `npm run watch`가 오늘 429가 있었는지를 `quota_hits_today`로 알린다
— 판정이 겉보기엔 잘 진행돼도(회차 안에서 몇 곳이라도 통과하면 기존
`consecutiveFailures`/`lastError`는 지워진다) 이 값은 남는다. 이게 자주
뜨면 이 배분을 다시 조율할 신호다.

### `점검 필요: 화제량 측정 부족` — 순위가 낡았다

카카오 블로그 검색이 막혔다는 뜻이다. 일 30,000 한도에 우리는 1,100 을 쓰므로
쿼터 문제일 가능성은 낮다. 키가 유효한지 먼저 본다.

```bash
npm run check-keys
```

### 링크를 눌렀는데 화면이 안 열린다

Vercel 문제다. 가장 흔한 원인은 **Vercel Authentication 이 다시 켜진 것**이다
(프로젝트를 다시 만들면 기본값으로 살아난다). 켜져 있으면 가족이 Vercel 로그인
화면을 만난다.

Vercel → 프로젝트 → Settings → Deployment Protection → **Vercel Authentication
= Disabled**

### 별점·다녀왔어요가 "설정 전" 이라고 나온다

`GITHUB_TOKEN` 이 만료·삭제됐다. 만료 없는 토큰을 쓰고 있으므로 누가 지운
경우다. 새로 만들어 **Vercel 환경변수**와 `.env` 두 곳에 넣는다.

- 권한: Contents(읽기·쓰기), Secrets(읽기·쓰기), Actions(읽기·쓰기)
- Resource owner: `shimdory-create`

### 카톡이 안 온다

발송은 카카오톡 커넥터를 쓰기 때문에 **금요일 정오에 이 PC 의 Claude Code 가
켜져 있어야** 한다. 꺼져 있었으면 그것이 원인이고, 링크는 언제 눌러도 최신이다.

완전 자동으로 만들려면 카카오 OAuth 토큰을 서버에 저장하는 작업이 필요하다
(아직 하지 않았다 — 필요해지면 그때).

### `폐업 확인 필요` 경고가 떴다 (maybe_closed)

카카오 장소 검색에서 21일 넘게 안 보이는 카페다. 발굴 잡은 새 카페만 넣으므로
폐업해도 목록에 남는다 — 그래서 주 1회 다시 찾아본다.

**바로 지우지 않는다.** 검색 순위 밖으로 밀렸거나 상호가 바뀐 것일 수도 있다.
지도에서 직접 확인한 뒤 내린다.

```bash
npm run hide -- "카페 이름"
```

되살리려면 `npm run hide -- --restore "카페 이름"`.

### 예전엔 있던 곳이 목록에서 안 보인다 (화제 식음 · dormant)

폐업이 아니다. 등록 후 180일이 지난 곳인데 화제량(블로그 언급)이 21일 연속
기준 미달이면 자동으로 `dormant` 상태로 넘어간다 — 활성 목록(daily-buzz의
매일 재측정 대상)에서 빠져서 git 저장소가 계속 커지는 걸 막는 예방 장치다
(2026-09-28, "화제 식음 후보" 설계). `excluded_auto`(신규 후보가 처음부터
탈락한 것)와 달리, 다녀온 기록이 있는 곳은 애초에 대상이 안 되고 — 이미
한 번 추천됐던 곳만 대상이다.

**완전한 삭제가 아니다.** `weekly-discover*.yml`과 같은 격주 주기로
(`npm run dormant-recheck` / `restaurant-` / `spot-` 접두), 화제량이 회복됐는지
자동으로 다시 확인해 통과하면 스스로 `active`로 돌아온다 — 사람이 손댈 일
없음. 지금 당장은 이 상태로 넘어가는 곳이 없다(2026-09-28 기준 어떤 곳도
등록 180일을 안 지났다 — 앱 자체가 2026-08-19에 생겼다) — 2027년 2월
이후부터 서서히 효과가 생기는 예방 장치다.

### 특정 지역 카페가 적다

대개 **수집이 안 된 것이 아니라 판정이 밀린 것**이다. 먼저 확인한다.

```bash
npm run health
```

그 지역만 몰아서 판정하려면:

```bash
npm run classify -- --limit 250 --order near
```

`near` 는 집에서 가까운 순이다. 평소에는 하루 몫의 30% 가 자동으로 거리순에
배정되므로(스펙 11.5) 며칠 지나면 저절로 메워진다.

### 열람용(동료용) 주소 — 이미 만들어져 있다

```
https://cafe-view-shim6.vercel.app
```

Vercel 프로젝트 `cafe-view` 가 가족용과 **같은 저장소**를 본다. 커밋이
올라가면 두 곳이 함께 배포된다. 환경변수는 없다.

쓰기 차단은 **주소로 판단한다** — host 가 `cafe-recommender` 로 시작하지
않으면 서버가 403 을 준다. 그래서 열람용에 무엇을 설정하든 쓰기는 열리지
않는다.

| | 가족용 | 열람용 |
|---|---|---|
| 주소 | `cafe-recommender-git-master-shim6` | `cafe-view-shim6` |
| 머리말 배지 | 없음 | **열람 전용** |
| 별점·다녀왔어요 | 가능 | 버튼 없음 · API 403 |
| 별점 표시 | 실시간 | 빌드 시점 (하루 단위) |

다시 만들 일이 생기면: [vercel.com/new](https://vercel.com/new) →
`shimdory-create/cafe-recommender` Import → 이름 `cafe-view` → Root Directory
`web` → Deploy.

**만든 직후 Vercel Authentication 을 꺼야 한다.** 새 프로젝트는 기본으로
켜져 있어서 동료가 Vercel 로그인 화면을 만난다 (2026-08-25 실제로 겪었다).

Settings → Deployment Protection → Vercel Authentication = **Disabled**

### 열람용에서 별점이 안 보인다

토큰 없이도 **빌드 시점 후기**가 보이게 해 뒀다 (하루에 한 번 갱신). 그것도
안 보이면 배포가 옛 코드인 것이다 — Vercel 에서 최신 커밋으로 다시 배포한다.

실시간으로 보이게 하려면 열람용 프로젝트에 **읽기 전용** GitHub 토큰을
넣는다 (Contents: Read). 쓰기는 어차피 host 로 막혀 있다.

### 판정이 전부 실패한다 (`source_failing`)

모델이 은퇴한 경우다. `gemini-3.1-flash-lite` 는 언젠가 사라진다.

`src/llm/` 의 모델 이름을 현재 무료 모델로 바꾸고 `npm test` 를 돌린다.
그다음 `npm run label -- --report` 로 품질이 유지되는지 확인한다
(기준선: 오통과율 5%, 경계 통과율 50%).

## 아무것도 안 했는데 멈출 수 있는 경로

결제 없이 도는 구조에서 진짜 위험은 돈이 아니라 **부패**다.

| 경로 | 대비 |
|---|---|
| 모델 은퇴 | 감시가 `source_failing` 으로 잡는다. 이름 한 줄 교체 |
| GitHub 액션 버전 만료 | v7 / Node 24 로 올려둠 (2026-08-21) |
| 토큰 만료 | 만료 없는 토큰. 만료를 걸면 그날 조용히 멈춘다 |
| Actions 무료 한도 (월 2,000분) | **2026-09월에 실제로 소진됐다** — 9/25 밤부터 2,079/2,000분으로 한도를 넘어 리셋(10/1)까지 daily-watch를 포함한 모든 워크플로가 조용히 멈췄다(실제 청구는 $0, 예산 $0가 정상 작동한 것). 원인은 `daily-buzz-restaurant`(활성 식당 전체를 매일 재측정) 하나가 식당 수가 4,200여 곳으로 늘면서 하루 6분→22분까지 커진 것 — 이게 월 예산의 약 30%를 혼자 썼다. **2026-09-28에 구조적으로 고쳤다**: `src/jobs/daily-buzz.ts`·`restaurant-daily-buzz.ts`·`spot-daily-buzz.ts`에 `ACTIVE_PER_DAY` 상한(카페 1,600·식당 1,500·가볼곳 900)을 추가해, `pending`과 같은 회전 방식(오래 안 잰 것부터)으로 active도 돌게 했다 — 데이터가 계속 늘어도 하루 비용이 여기서 더 안 커진다. 같은 날 `weekly-discover*`(신규 발굴, 3도메인 합쳐 월 180~360분)도 매주에서 격주로 낮췄다 — `scripts/biweekly-gate.sh`가 잡 맨 앞에서 "이번이 실행 주인지" 스스로 판단해 아니면 뒷 스텝을 건너뛴다(GitHub Actions 크론은 격주를 직접 지원 안 함). 실존확인(weekly-liveness)은 그대로 매주다. 그래도 [GitHub 사용량](https://github.com/settings/billing/summary)은 가끔 확인한다 — 이 두 조치로 월 사용량이 2,079분→1,200~1,400분대로 내려갈 것으로 예상하지만(2026-09-28 추정), 데이터가 계속 늘면 다른 잡도 조금씩 커질 수 있다. 한도를 넘으면 돈이 나가지 않고(예산 $0로 막아둠) 그 달 남은 기간 동안 **모든 워크플로가 조용히 멈춘다** — daily-watch도 같이 멈추므로 이 경우엔 카톡도 안 온다(GitHub이 이메일로 별도 안내할 수는 있음). |

## 자주 쓰는 명령

```bash
npm run watch          # 운영 이상 점검 (키 없이 돈다)
npm run audit          # 데이터 정합성 점검 (키 없이 돈다)
npm run requeue -- --dry   # 컷이 바뀐 뒤 되살릴 배제분 미리보기
npm run liveness       # 폐업 감지 — 카카오에 아직 있는지 다시 찾아본다
npm run dormant-recheck   # 화제 식음 후보 재확인 (보통 격주 자동 실행, 수동도 가능)
npm run normalize      # 시군구를 주소 기준으로 정정 (멱등)
npm run health         # 데이터 현황과 소스 상태
npm run notify         # 카톡 문구 미리보기 (발송 안 함)
npm run label -- --report   # 골든셋 품질 기준선
npm run inspect -- "카페명"  # 한 곳의 판정 근거 확인
```

Bash 로 돌릴 때는 `export PATH="/c/Program Files/nodejs:$PATH"` 를 먼저 붙인다.
