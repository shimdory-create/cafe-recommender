## 1. 무엇을 만드는가, 왜 두 단계인가

카페·식당과 같은 틀로 **가볼 곳**(자연/공원, 관광지/명소, 시장/전통거리,
쇼핑/아울렛, 전시/박물관, 소품샵/편집숍, 드라이브, 체험, 계절명소, 아이와
가기 좋은 곳) 추천을 만든다 — 세 번째 도메인이다.

**이 문서는 1단계만 다룬다 — 데이터 파이프라인.** 화면(웹)에는 아직 아무것도
안 보인다. 2단계(웹 화면, 3-way 전환 스위치)는 1단계 데이터가 실제로
쓸만한지 확인한 뒤 별도 스펙으로 진행한다. 코스 추천(카페+식당+가볼 곳을
하루 일정으로 묶는 것)은 2단계까지 끝난 뒤 완전히 새로운 브레인스토밍으로
다룬다 — 이 문서의 범위가 아니다.

**최우선 제약은 카페·식당 때와 동일: 지금 배포된 카페·식당 추천 화면과
파이프라인은 한 줄도 동작이 바뀌지 않는다.** 새 파일, 새 잡, 새 워크플로만
추가한다.

## 2. 카페·식당과 다른 점

| 항목 | 카페 | 식당 | 가볼 곳 |
|---|---|---|---|
| 검색어 | "대형카페", "베이커리카페" 등 | "한식 맛집" 등(음식종류별) | "관광명소", "공원", "전시관" 등(카테고리별) |
| 관련성 판별 | 카페·베이커리·커피 단어 | 식당·맛집·메뉴 단어 | 가볼곳·나들이·명소·데이트 단어 |
| 제외 목록 | 스터디카페 등 부속 유형 | 프랜차이즈·패스트푸드, 배달·포장 전용, 술집·호프 | **1차는 없음** (아래 3절 참고) |
| 분류 축 | 성격 태그 8개(다중) | 음식 종류(단일값) | **성격 태그 10개(다중, 카페와 같은 AND 조합 방식)** |
| 가족적합도 보너스 | `menuLevel` | 룸/개별공간, 예약 가능 | **주차 + 이동시간 + "아이와 가기 좋은 곳" 태그 가산점** |
| 새로 추가되는 속성 | — | — | **체류시간, 실내/실외, 계절**(로직 없이 저장만 — 6절 참고) |
| LLM 프롬프트 | "한국 카페 정보를 구조화" | "한국 식당 정보를 구조화" | "가볼 곳 정보를 구조화" — 태그·체류시간·실내외·계절·주차 근거 추출 |
| 게이트(`pipeline/gate.ts`) | 성격 태그 0개 배제, 주차 D 배제 | 음식종류 미분류 배제, 주차 D 배제 | **태그 0개 배제, 주차 D 배제 (카페와 완전히 같은 규칙 — `passesHardGate` 그대로 재사용)** |

식당 때 실수로 배웠던 것 하나를 여기서 미리 반영한다: **태그는 카페처럼
다중 선택 + AND 조합**이다. 식당의 음식종류(정확히 하나만 갖는 값)와
달리, 가볼 곳은 한 장소가 "자연" 이면서 동시에 "아이와 가기 좋은 곳"일 수
있다 — 단일 선택으로 잘못 설계하면 식당 2단계에서 났던 것과 같은 종류의
버그(칩 2개 고르면 결과 0개)가 똑같이 난다. 이 문서가 이미 다중 선택으로
못을 박아 두는 이유다.

## 3. 데이터 구조

카페·식당과 완전히 분리된 파일·타입을 쓴다. 세 도메인을 공용 `Place`
타입으로 합치는 리팩터는 **지금 하지 않는다** — 위험 부담이 크고, 지금까지
이 프로젝트가 잘 굴러간 이유가 "도메인끼리 서로 영향 0"이었던 원칙을
깨게 된다. 통합은 세 도메인이 전부 안정화된 뒤 별도의 순수 리팩터
작업(기능 변경 없는 타입 정리)으로 미룬다.

- `data/spots.json`, `data/spot-buzz.json`, `data/spot-suggestions.json` — 새 파일. 기존 `data/cafes.json`, `data/restaurants.json` 등은 안 건드린다.
- `SpotSchema`, `SpotAttributesSchema` — `src/spot-schema.ts`에 새로 정의 (카페의 `schema.ts`, 식당의 `restaurant-schema.ts`와 같은 이유로 분리 — 파일이 커지는 것을 막고, 어디가 공용이고 어디가 전용인지 흐려지지 않게 한다).
- **순수 계산 함수는 그대로 import해서 쓴다** — `geo.ts`, `district.ts`, `region-match.ts`, `place-query.ts`, `config/area.ts`·`zones.ts`·`regions.ts`, `pipeline/gate.ts`(`passesHardGate` 그대로), `pipeline/score.ts`(`hotScore`/`finalScore` 그대로). 이 모듈들은 좌표·날짜만 다루고 특정 도메인 타입을 참조하지 않는다 — 카페·식당 때 이미 실측으로 확인된 사실이 그대로 적용된다.
- **저장소를 직접 읽고 쓰는 잡은 얇게 복사한다** — `spot-liveness.ts`, `spot-drive-times.ts`를 새로 만든다(카페의 `liveness.ts`/`drive-times.ts`를 얇게 복사했던 것과 같은 이유 — 제네릭화하면 기존 도메인 코드를 건드리게 된다).
- `buzz.ts`의 점수 계산 수식은 그대로 재사용하고, "이 글이 진짜 가볼 곳 얘기인가" 판별(`isRelevant`)만 가볼 곳판으로 교체해서 부른다.
- 가족적합도 공식(`spotFamilyFit`)은 새로 만든다. 정확한 가중치는 구현 중
  정하되, 대략 `주차등급 + 이동시간 + ('아이와 가기 좋은 곳' 태그가 있으면
  가산점)` 형태가 될 것으로 예상한다 — 카페의 `menuLevel`, 식당의
  룸/예약 자리에 들어가는 항목이다.

## 4. 실행 방식

- **CLI**: `src/cli/run.ts`에 `spot-discover`, `spot-buzz`, `spot-classify`, `spot-suggest`, `spot-liveness`, `spot-drive` 등 새 케이스를 추가한다. 기존 케이스는 그대로 둔다 — 추가만 하고 아무것도 바꾸지 않는다. `MUTATING` Set에도 6개 다 추가한다(식당 1단계 때 `restaurant-liveness`를 빠뜨렸다가 최종 리뷰에서 발견해 고쳤던 실수를 이번엔 계획 단계부터 반영한다).
- **GitHub Actions**: 카페·식당 워크플로와 이름만 다른 병렬 워크플로(`daily-buzz-spot.yml`, `weekly-discover-spot.yml` 등) 6종을 새로 만든다.
- **동시성 그룹은 처음부터 `data-write`로 공유한다.** 식당 1단계 때 별도
  그룹(`restaurant-data-write`)으로 시작했다가 2단계 최종 리뷰에서
  "결국 같은 `web/src/generated/` 생성물을 공유하니 분리하면 안 된다"는
  걸 발견해 나중에 통합했던 시행착오가 있었다 — 이번엔 그 결론을 알고
  있으니 처음부터 `data-write` 하나로 합친다.
- **커밋·푸시는 처음부터 공용 스크립트(`scripts/commit-data.sh`)를 쓴다.**
  식당 1단계 때는 "카페 페이로드만 재생성하니 낭비"라며 직접 커밋하는
  코드를 6곳에 복붙했다가, 2단계에서 `npm run site`가 여러 도메인
  페이로드를 함께 만들도록 바뀐 뒤에도 그 사실이 반영이 안 돼 화면이
  갱신되지 않는 버그로 이어졌다. 이번엔 그 교훈을 안다 — 처음부터
  공용 스크립트를 쓰면 이 문제 자체가 생기지 않는다.
- **API 키는 그대로 공유한다** (`KAKAO_REST_API_KEY`, `GEMINI_API_KEY`).

### 파일럿 범위

가볼 곳의 태그 분류(10개 카테고리, 다중 선택)는 카페·식당과 다른 새로운
LLM 분류 작업이라, 전체 66개 시군구를 한 번에 돌리지 않는다. 식당 때와
같은 방식으로 **집 근처 5개 시군구(부평구·계양구·서구·김포시·검단구)만
먼저 돌려서** 분류 정확도와 게이트 규칙이 실제로 쓸만한지 확인한 뒤 전체로
넓힌다. 식당 1단계 때 이 파일럿 검증이 실제로 유용했다(전체 확장 전에
분류 방식을 다듬을 기회가 됐다) — 같은 방식이 안전하다.

## 5. 테스트 방침

카페·식당 파이프라인의 테스트 스타일(순수 함수 단위 테스트, 잡은 store를
목으로 주입)을 그대로 따른다. `tests/pipeline/`, `tests/jobs/` 아래
`spot-*.test.ts`로 나란히 둔다. 기존 카페·식당 테스트는 건드리지 않는다 —
실행해서 전부 그대로 통과하는지가 "서로 영향 0"의 실측 증거다.

## 6. 새 속성(체류시간·실내외·계절)의 범위

세 속성 모두 **LLM 추출 프롬프트에 항목만 추가하는 것으로 끝낸다** —
카페의 `stayDuration` 필드가 이미 같은 방식(블로그 글에서 LLM이 추출,
없으면 null)으로 존재하므로 완전히 같은 패턴을 재사용한다. 추가 수집
비용은 사실상 0이다(어차피 하는 LLM 호출 한 번에 필드만 몇 개 더 물어보는
것).

- `stayDuration: string | null` — 카페와 동일한 형태.
- `indoorOutdoor: 'indoor' | 'outdoor' | 'mixed' | null` — 새 필드.
- `season: '봄' | '여름' | '가을' | '겨울' | '사계절' | null` — 새 필드.

**의도적으로 이번 단계에 안 넣는 것:** 이 세 값을 이용한 자동 랭킹/필터
로직(예: "지금이 가을이니 단풍명소에 가산점", "비 오는 날엔 실내만
보여주기"). 이건 저장은 해 두고 로직은 안 만든다 — 만들려면 "이번 주
추천"을 다시 설계해야 하고, 그건 이 문서 범위 밖인 코스 추천 단계의
일이다. 지금 데이터만 쌓아 두면 그 단계에서 새로 수집할 필요 없이 바로
쓸 수 있다.

## 7. 범위 밖 (뒤로 미룬다)

- 웹 화면 반영 (3-way 전환 스위치, `/spot` 경로 5개, API 라우트 4종) — 2단계 스펙에서 따로 다룬다.
- 계절·날씨 기반 자동 랭킹, 코스 추천(카페+식당+가볼 곳을 하루 일정으로 묶기) — 완전히 새로운 브레인스토밍으로, 2단계 이후에 다룬다.
- `Cafe`/`Restaurant`/`Spot`을 공용 `Place` 타입으로 합치는 리팩터.
- 제외 규칙(블랙리스트) 정교화 — 1차는 아예 없이 시작하고, 실제로 걸러야 할 사례가 나오면 그때 추가한다.
- 가족 구성원별 취향 학습, 카톡 투표 등 — 로드맵 후반부 항목들, 아직 이 프로젝트의 범위로 확정되지 않았다.
