## 2. 발견 C — `firstPostDate` 는 카페 나이가 아니다

### 무엇이 틀렸나

`computeBuzz` 의 `firstPostDate` 는 **최신 50건 창(window) 안의 관련 문서 중
가장 오래된 것**의 날짜다. 카카오 블로그 검색은 최신순 50건만 주므로, 이 값은
"카페에 관한 첫 글"이 아니다.

그런데 두 곳에서 이것을 카페 나이로 취급한다.

1. `passesLayer2` 의 "신규 오픈 구제" — `firstPostDate` 가 180일 이내면 통과
2. `hotScore` 의 `novelty` — `ageDays <= 180` 이면 만점 0.10

**글이 많은 카페일수록 50건 창이 짧아진다.** 10년 된 유명 대형카페도 최근
한 달에 50건이 쌓이면 `firstPostDate` 가 30일 전이 되어 "신규"로 판정된다.
방향이 거꾸로다.

### 실측 영향

```
정밀도 통과 3,296곳 중 "180일 이내" 판정      1,218곳 (37%)
그중 relevantCount < 10                          22곳
그중 월 8건 미만 (구제로만 통과)                238곳
```

- **`novelty` 항은 사실상 포화되었다.** 37%가 만점을 받으며, 그 37%는
  "글이 많아서 창이 짧은" 카페들이다. 즉 `novelty`(0.10)가 `volume`(0.30)을
  중복 계산하고 있다. 순위를 크게 뒤집지는 않지만(둘이 같은 방향) 설계 의도인
  "새로 뜬 곳 가점"은 작동하지 않는다.
- **Layer 2 구제는 238곳을 추가로 통과시킨다** (통과분의 19%). 이들은 월 8건
  미만이며, 신규 오픈이 아니라 "글이 꾸준히 조금씩 있는" 카페일 가능성이
  높다. 동네 카페 오통과의 주요 경로 후보다.

### 지금 고치지 않는 이유

임계값을 만지는 것이 아니라 **지표의 의미가 틀린** 문제이므로 대안이 필요한데,
현재 데이터 소스로 "카페 나이"를 알 방법이 없다. 50건 창 밖의 과거 글은 보이지
않는다. 후보는 세 가지다.

| 대안 | 방법 | 비용 |
|---|---|---|
| (a) 구제에 최소 볼륨 조건 추가 | `posts30d >= 3` 등 | 0. 통과 1,235 -> 1,167 |
| (b) `novelty` 항 제거 | 가중치를 `volume` 으로 흡수 | 0 |
| (c) 카페 나이를 별도 조회 | `sort=accuracy` 로 오래된 글 확인 | 호출 2배 |

(a)와 (b)는 공짜지만 **238곳이 동네 카페인지 아닌지 근거가 없다.** 골든셋
경계 구간에 이 238곳을 의도적으로 포함시켜 O/X 를 받으면 답이 나온다.
그때까지 현행을 유지한다 — 양평 발견 B 와 같은 판단이다.

### 계획 2에서 측정할 것

- 층화 추출의 **경계 구간 10곳을 "구제로만 통과한 238곳"에서 뽑는다**
  - `X` 가 많으면 -> (a) 채택, `posts30d >= 3` 추가
  - `O` 가 많으면 -> 구제는 유효하며 이름만 바꾼다
- `novelty` 는 골든셋과 무관하게 (b)로 정리해도 안전하다. 다만 상위 순위가
  바뀌는지 확인 후 커밋한다

## 2.5 발견 D — 근거 없는 상향 판정 (프롬프트 p2 로 수정)

200곳 판정 후 통과분을 사람이 읽었다. 종로구 6곳에서 세 필드가 규칙 1
("후기에 없는 것을 추측하지 마라")을 무시하고 있었다.

| 카페 | 근거 | p1 판정 | 문제 |
|---|---|---|---|
| 에이라운드 | "매장 앞 1대 이용 중에 무료 주차 가능" | 주차 **B** · 규모 **대형** | 1대는 협소가 아니라 사실상 불가. 규모 근거는 아메리카노 가격뿐 |
| 테라로사 광화문점 | "1만원 이상 1시간 무료" 건물 지하주차장 | 주차 **A** | 전용도 아니고 조건부다 |
| 넬보스코 남촌빵집 | "지하주차장 1시간 무료주차" | 주차 **A** | 같음 |
| 피그먼츠 을지로입구점 | "주말 2시간 무료" | 주차 **A** | 같음 |
| 리제로 서울 | 뷰 언급 없음 | 뷰 **3** · viewTypes **["도심"]** | 도심에 있다는 것이 뷰가 아니다 |

**주차는 게이트다.** 인플레가 곧 헛걸음이 되고, 그것이 성공 기준 4
("주차 때문에 헛걸음 0회")를 직접 깬다. 토요일 오후 도심 건물 주차장의
"1시간 무료"는 만차다.

`viewStrength` 분포도 0 / 3 / 5 세 값에만 몰려 있었다(19 / 18 / 18).
프롬프트가 예시로 준 값을 그대로 돌려주고 있었다는 뜻이다.

### 수정과 검증 (p1 -> p2 A/B)

프롬프트에 **필드별로 "무엇이 있어야 그 값을 쓸 수 있는지"**를 못 박았다.
임계값을 옮긴 것이 아니라 정의를 좁혔다.

같은 55곳을 재추출했다 (`classify --redo-stale`). 35곳은 p1 값을 보존해
카페별로 비교했다.

```
주차  8건 정정 — 전부 하향. 상향은 0건
        테라로사 광화문 A->B   넬보스코 A->B   피그먼츠 A->B
        에이라운드 B->C        언더스탠드커피 B->C   -> 둘 다 게이트 탈락
        라파리나·미드메·솔방울베이커리 C->D
규모  10건 -> 전부 null (좌석·층수 근거 없음)
뷰     3건 하향 (퍼먼트 안국 3->0, 도트블랭킷 삼청 3->0, 카페진선 5->3)
통과  28곳 -> 25곳
```

**에이라운드는 p1 에서 종합 3위였다.** 주차 1대로 탈락했다. 게이트가
의도대로 동작한 것이다.

`assignTags` 에는 규칙 하나를 더했다: 뷰 종류가 '도심' 뿐이면 임계 +1.
남산·한강 스카이라인처럼 진짜 도심 뷰는 후기가 압도적으로 쓴다.

### 남은 것

- `PROMPT_VERSION` 을 `modelVersion` 에 붙였다(`gemini-3.1-flash-lite+p2`).
  다음에 프롬프트를 고치면 `--redo-stale` 로 재추출 대상을 골라낸다
- **p1 값을 커밋 전에 재추출해서 첫 20곳의 카페별 비교를 잃었다.** 집계만
  남았다. 판정 데이터는 재추출 전에 반드시 먼저 커밋한다

## 3. 용량 — 카페 수 4배가 곱셈마다 4배로 번졌다

스펙의 용량 추정은 전부 **카페 1,500곳** 전제였다. 실측 6,216곳이다.

| 파일 | 스펙 추정 | 실측 | 처리 |
|---|---|---|---|
| `cafes.json` | 약 1.5MB | 4.7MB | 감당 가능 |
| `buzz.json` (180일 롤링) | 약 100MB | **403MB** | 최신 1건 보관으로 변경 |
| `data/raw/` | — | 36.4KB x 1,500/일 = 53MB/일 | gitignore |

`buzz.json` 은 180일 이력을 **읽는 코드가 하나도 없었다.** 가속도는 방금 받은
50건 창에서 계산하고, 판정·추천은 최신 1건만 조회한다. 순수 비용이었다.
추이 그래프가 필요해지면 월 1건 집계 파일을 따로 두는 것이 맞다.

**교훈**: 곱셈이 들어간 추정치는 승수의 실측이 나온 직후 전부 재검산한다.

## 4. 개선 후보 — 자동차 길찾기로 실주행 시간

`geo.ts` 는 직선거리 x 1.35 로 근사하며 실측 오차가 방향까지 갈린다.

```
양평  추정 91분 / 실제 약 80분    과대
가평  추정 106분 / 실제 약 90분   과대
강화  추정 29분 / 실제 약 60분    과소 2배
파주  추정 43분 / 실제 약 60분    과소
```

강화도·파주는 **다리와 우회로 때문에** 직선거리 근사가 무너진다. 가족 나들이
판단에서 "29분"과 "60분"은 다른 결정이다.

카카오 **자동차 길찾기 무료 한도 10,000건/일** 이 확인되었으므로 실주행 시간을
직접 받을 수 있다. 게이트 통과분(현재 1,235곳 이하)에 한해 주 1회 갱신하면
호출량은 무해하다. **계획 2 완료 후 최우선 개선 후보**로 기록한다.
