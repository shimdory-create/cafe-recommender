## 1. 무엇을 만드는가, 왜 두 단계인가

카페 추천과 같은 틀로 식당(한식·일식·중식·양식·분식 등) 추천을 만든다.
가족이 "카페 먼저 찾고 근처 식당" 또는 그 반대로 엮어 보고 싶어 해서,
데이터가 같은 파이프라인 모양(좌표·거리·화제량)으로 나오는 것이
장기적으로 맞다고 판단했다.

**이 문서는 1단계만 다룬다 — 데이터 파이프라인.** 화면(웹)에는 아직 아무것도
안 보인다. 2단계(탭 구성, 통합 여부, 연관 검색)는 1단계 데이터가 실제로
쓸만한지 확인한 뒤 별도 스펙으로 진행한다.

**1단계의 최우선 제약: 지금 배포된 카페 추천 화면과 카페 파이프라인은
한 줄도 동작이 바뀌지 않는다.** 새 파일, 새 잡, 새 워크플로만 추가한다.

## 2. 카페와 다른 점

파이프라인 코드를 먼저 조사했다. 지역 설정·거리 계산·화제량 집계 수식·
폐업 감지·중복 제거 같은 큰 덩어리는 이미 "장소"라는 개념에만 기대고
있어 카페와 무관하게 재사용 가능하다. 카페 전용 로직은 다섯 곳에 몰려
있고, 식당은 이 다섯을 새로 쓴다.

| 항목 | 카페 | 식당 |
|---|---|---|
| 검색어 (`config/keywords.ts`) | "대형카페", "베이커리카페" 등 | "한식 맛집", "일식 맛집" 등 (음식종류별) |
| 관련성 판별 (`pipeline/relevance.ts`) | 카페·베이커리·커피 단어 | 식당·맛집·메뉴 단어 |
| 제외 목록 (`pipeline/exclude.ts`) | 스터디카페 등 부속 유형 | 프랜차이즈·패스트푸드, 배달·포장 전용, 술집·호프 |
| 분류 축 (`pipeline/tag.ts`) | 성격 태그 8개(대형베이커리·뷰맛집 등) | **음식 종류**(한식/일식/중식/양식/분식/고기 등, 단일 값) |
| 가족적합도 보너스 (`pipeline/score.ts`) | `menuLevel`(식사 가능 여부) | **룸/개별공간 여부**, **웨이팅 없음·예약 가능 여부** |
| LLM 프롬프트 (`llm/prompts.ts`) | "한국 카페 정보를 구조화" | "한국 식당 정보를 구조화" — 음식종류·룸·웨이팅·주차 근거 추출 |
| 게이트(`pipeline/gate.ts`) | 성격 태그 0개 배제, 주차 D 배제 | 음식종류 미분류 배제, 주차 D 배제 (카페와 동일) |

`menuLevel` 이 빠지는 자리는 스코어링에서 제거하고, 룸·웨이팅 두 축을
새 보너스 항으로 넣는다 (가중치는 구현 중 카페의 `PARKING_MULT` 등과
같은 자리에서 정한다).

## 3. 데이터 구조

카페와 완전히 분리된 파일·타입을 쓴다. 하나로 합치는 리팩터(`Cafe`→`Place`
제네릭화)는 지금 하지 않는다 — 기존 카페 코드를 건드리는 순간 "카페 영향
0" 이 깨지기 때문이다. 안정화된 뒤 나중에 합칠 수 있다.

- `data/restaurants.json`, `data/restaurant-buzz.json`, `data/restaurant-suggestions.json` — 새 파일. `data/cafes.json` 등 기존 파일은 안 건드린다.
- `RestaurantSchema`, `RestaurantAttributesSchema` — `src/restaurant-schema.ts` 에 새로 정의 (기존 `schema.ts` 에 얹지 않는다 — 파일이 이미 크고, 두 도메인을 한 파일에 섞으면 어디가 공용이고 어디가 전용인지 흐려진다).
- **순수 계산 함수는 그대로 import 해서 쓴다** — `geo.ts`(거리 근사), `district.ts`(주소→시군구), `region-match.ts`, `place-query.ts`, `config/area.ts`·`zones.ts`·`regions.ts`. 이 모듈들은 좌표·날짜만 다루고 `Cafe` 타입을 참조하지 않는다 — 실측으로 확인했다.
- **저장소를 직접 읽고 쓰는 잡은 얇게 복사한다** — `liveness.ts`, `drive-times.ts` 는 지금 `Cafe[]` 를 직접 읽고 쓰게 짜여 있다. 제네릭화하면 카페 쪽 코드를 건드리게 되므로, 1단계에서는 `restaurant-liveness.ts`, `restaurant-drive-times.ts` 로 복사해 식당 스토어만 본다. 로직은 거의 같지만 파일은 분리한다.
- `buzz.ts` 의 점수 계산 수식(`computeBuzz` 등)은 그대로 재사용하고, "이 글이 진짜 식당 얘기인가" 판별(`isRelevant`)만 식당판으로 교체해서 부른다.

## 4. 실행 방식

- **CLI**: `src/cli/run.ts` 에 `restaurant-discover`, `restaurant-buzz`, `restaurant-classify`, `restaurant-suggest` 등 새 케이스를 추가한다. 기존 케이스(`discover`, `buzz` ...)는 그대로 둔다 — 추가만 하고 아무것도 바꾸지 않는다.
- **GitHub Actions**: 카페 워크플로와 이름만 다른 병렬 워크플로(`daily-buzz-restaurant.yml`, `weekly-discover-restaurant.yml` 등)를 새로 만든다.
- **동시성 그룹은 분리한다.** 지금 데이터 쓰기 워크플로는 전부 `data-write` 그룹 하나로 직렬화된다 (같은 `web/src/generated/site.json` 을 다시 만들기 때문). 식당은 다른 파일에 쓰므로 겹칠 이유가 없다 — `restaurant-data-write` 그룹을 따로 둬서 카페 잡과 서로 기다리지 않게 한다.
- **API 키는 그대로 공유한다** (`KAKAO_REST_API_KEY`, `GEMINI_API_KEY`). 새 키는 필요 없지만, 무료 일일 한도를 카페·식당이 나눠 쓰게 된다 — 사용량은 지켜봐야 한다. `usage-watch` 의 쿼터 소진 감지는 이미 범용이라 그대로 적용된다.

### 파일럿 범위

66개 시군구 전체를 한 번에 돌리지 않는다. **집 근처 5~10개 시군구만
먼저 돌려서** 음식종류 분류와 게이트 규칙이 실제로 가족이 보기에
쓸만한지 확인한 뒤 전체로 넓힌다. 카페도 처음에 이런 검증 라운드를
여러 번 거쳤다 — 같은 방식이 안전하다.

## 5. 테스트 방침

카페 파이프라인의 테스트 스타일(순수 함수 단위 테스트, 잡은 store를
목으로 주입)을 그대로 따른다. `tests/pipeline/`, `tests/jobs/` 아래
`restaurant-*.test.ts` 로 나란히 둔다. 기존 카페 테스트는 건드리지 않는다
— 실행해서 전부 그대로 통과하는지가 "카페 영향 0" 의 실측 증거다.

## 6. 범위 밖 (2단계로 미룬다)

- 웹 화면 반영 (탭 구성, 통합 리스트 여부)
- "이 카페 근처 식당" 연관 검색
- 위시리스트·다녀온 곳 같은 기존 가족 기능과의 통합
- `Cafe`/`Restaurant` 를 공용 `Place` 타입으로 합치는 리팩터
