# 수도권 대형카페 가족 추천 서비스 — 설계 문서

- 작성일: 2026-08-19
- 상태: 승인됨 (구현 계획 작성 대기)

---

## 1. 무엇을 만드는가

인천 부평 거주 4인 가족이 **월 2회 주말 대형카페 나들이**를 결정하고 기록하는
가족 전용 웹서비스.

핵심 정체는 "카페 검색 앱"이 아니다. 검색은 네이버지도·카카오맵·인스타가
이미 훨씬 잘한다. 이 서비스가 푸는 문제는 다르다.

> 인스타에서 본 카페가 흩어져 있고 → 주말마다 "어디 갈까"를 처음부터
> 다시 고민하고 → 4명 취향이 다르고 → 다녀온 데가 좋았는지 기억에 안 남는다.

따라서 이 서비스는 **주말 카페 의사결정 + 기록 앱**이다.

## 3. 핵심 루프 (v2 — 읽기 중심)

v1의 루프에서 **투표와 평점 기록을 걷어냈다.** 쓰기 기능이 유지보수
부담의 거의 전부이기 때문이다 (4절 목표 2 참조).

```
① 수집   배치가 매일 돌며 "지금 뜨는 곳" 리스트를 자동 갱신
    v
② 알림   매주 금요일 정오, 카카오톡으로 링크가 온다
    v
③ 열람   가족 모두가 같은 리스트를 본다. 로그인 없음, 조작 없음
    v
④ 결정   가족 단톡방에서 말로 정한다  <- 앱이 하지 않는다
    v
⑤ 표시   다녀오면 "다녀왔어요" 토글 1개. 익명
    v
⑥ 배제   다녀온 곳은 추천에서 내려간다 -> ①로
```

**④를 앱이 하지 않는 것이 이 설계의 핵심이다.** 가족 단톡방은 이미
존재하는 최고의 투표 도구다. 앱이 그것을 흉내 내면, 아무도 쓰지 않는
투표 UI와 그것을 떠받치는 인증·상태관리·정합성 문제만 남는다.

**⑤ 토글 1개는 포기할 수 없다.** 없으면 월 2회 x 1년 = 24곳이 계속
추천 상단에 뜨고 `unvisited_mult`(8.2절)가 죽는다. 이것이 서비스 전체에서
**유일하게 남는 쓰기 기능**이며, 익명 토글이라 인증이 필요하지 않다.

## 4. 설계 목표와 비목표

### 목표
1. **계정 정지 리스크 0** — 로그인이 필요한 서비스를 자동화하지 않는다
2. **유지보수 최소** — HTML 파서를 한 줄도 쓰지 않는다
3. **운영비 0원 수준** — 무료 티어 안에서 돌아간다
4. **동네 카페가 안 나온다** — 이것이 품질의 체감 기준
5. **주차 안 되는 곳이 안 나온다** — 차량 이동 가족의 절대 조건

### 비목표 (의도적 제외)
- 대중 서비스화, 회원 가입, 확장성
- 실시간성 (1~2주 후행 지연을 수용한다)
- 완벽한 자동 판정 (사람이 손으로 고치는 경로를 항상 둔다)

## 6. 데이터 수집 전략 — "크롤링 없는 자동 수집" (v3)

> **v3 개정 (2026-08-20).** 네이버 검색 API의 신규 발급 경로가 사라져
> **카카오 하나로 통일**했다. 실측 근거는
> `2026-08-20-data-source-findings.md` 에 있다.

### 6.1 왜 크롤링을 하지 않는가

크롤링은 두 개의 독립된 문제를 만든다.

| 문제 | 원인 | 크롤링 | 공식 API |
|---|---|---|---|
| 유지보수 지옥 | DOM이 바뀌면 파서가 조용히 깨진다 | 상시 발생 | 스키마 안정 |
| 계정 정지 | 로그인 필요 서비스를 자동화 | 인스타는 로그인 필수 | 로그인 자체가 없음 |

특히 인스타는 로그인 없이 사실상 아무것도 볼 수 없다. 즉
**인스타를 크롤링한다 = 정지될 계정을 반드시 만든다**는 뜻이다.
이 리스크는 줄이는 것이 아니라 만들지 않는 것만 가능하다.

### 6.2 "핫함"을 인스타 없이 측정하는 방법

한국인의 행동 패턴을 이용한다.

```
인스타에서 봄  ->  네이버에 검색함  ->  블로그 후기가 쏟아진다
  (원인)          (1~2주 후행)       (측정 가능)
```

**네이버 블로그 포스팅의 가속도**가 인스타 바이럴의 대리 지표가 된다.
월 2회 방문하는 가족에게 1~2주 지연은 실질적 손실이 없다.

**여기서 v3의 핵심:** 네이버 블로그 글을 읽기 위해 네이버 API가 필요하지
않다. **다음(카카오) 검색이 네이버 블로그를 충실히 색인한다.** 실측에서
관련 문서의 대부분이 `naver.com` 도메인이었다 (테라로사 46/48, 더티트렁크
42/43). 네이버 블로그라는 *신호*는 카카오라는 *창구*로 그대로 얻는다.

### 6.3 사용 API (v3 — 키 2개)

| API | 용도 | 인증 | 사용량 |
|---|---|---|---|
| 카카오 로컬 (키워드 검색) | 후보 발굴, 장소 정규화 | 카카오 REST 키 | 약 1,700/월 |
| 카카오 블로그 검색 (다음) | 화제량 측정, 속성 근거, 그물 C | **같은 키** | 약 1,500/일 |
| Gemini `gemini-3.1-flash-lite` | 속성 구조화 추출, 큐레이션 수확 | Gemini 키 | 신규 카페만 |

**관리할 키는 2개다.** 카카오 하나, Gemini 하나.

> **네이버는 쓰지 않는다.** 2026-06-25 검색 API가 NAVER API HUB(NCP)로
> 이관되어 신규 신청자는 NCP 계정 + 종량제를 써야 한다. 실제로
> `developers.naver.com` 등록 화면의 [사용 API] 드롭다운에 "검색" 항목이
> 없다. 유지보수 최소화 목표에도 어긋나므로 채택하지 않는다.

> **Anthropic API 는 쓰지 않는다.** 무료 티어가 없고 최소 $5 선불 충전이
> 필요하다. 예상 비용은 작았지만(초기 약 9,000원 + 월 약 400원) 무료
> 경로를 우선했다. LLM 어댑터는 provider-agnostic 하므로 언제든 교체된다.

### 6.4 세 개의 그물 (Recall 우선)

| 그물 | 방법 | 잡는 것 |
|---|---|---|
| **A. 카카오 키워드** | `{시도} {시군구} x 6키워드 x 3페이지` | 상호·태그로 잡히는 곳 |
| **B. 카카오 카테고리** | 좌표 기반 `CE7` 반경 검색 | 카테고리로 잡히는 곳 |
| **C. 블로그 큐레이션 수확** | 6.5절 | **사람이 인정한 곳** |

키워드 6종: `베이커리카페` `대형카페` `브런치카페` `루프탑카페` `정원카페` `뷰맛집카페`

**그물 C가 왜 필요한지 실측으로 확인됐다.** `"양평 베이커리카페"` 로 카카오
키워드 검색을 돌렸을 때 1위가 **커피전문점** 카테고리의 무관한 카페였다.
카카오 키워드 검색은 상호명 매칭 위주라 **상호에 "대형"이 없는 대형카페를
놓친다.** 그물 C가 이 구멍을 메운다.

### 6.5 블로그 큐레이션 수확 (가장 정확한 그물)

블로거들은 이미 `"양평 대형카페 BEST 7"` 같은 글을 쓴다. 이것은
**사람이 손으로 큐레이션한 결과물**이며 동네 카페는 여기 나오지 않는다.

```
1. 카카오 블로그 검색: "{시군구} 대형카페 추천"
                       "{시군구} 베이커리카페 뷰"
                       "{시군구} 카페 베스트"
2. 스니펫 확보 (요청당 50건)
3. Gemini 에 투입 -> 언급된 카페 상호명만 추출
4. 카카오 로컬로 조회 -> 좌표·주소·카테고리 정규화
5. kakaoPlaceId 로 중복 제거
```

정규화 기준키는 **`kakaoPlaceId`** 로 고정한다. 상호명은 표기가 흔들리므로
절대 기준키로 쓰지 않는다.

### 6.6 어댑터 패턴 + 우아한 저하

유지보수 난이도를 구조적으로 낮추는 세 원칙.

**원칙 1 — 소스는 독립 어댑터.** 각 소스는 같은 인터페이스를 구현하며
서로를 모른다. 하나가 죽어도 나머지로 점수를 계산하고, `npm run health` 에
"카카오 블로그 3일째 실패" 가 뜬다. 서비스는 멈추지 않는다.

**원칙 2 — 원본 응답 스냅샷 저장 (로컬 전용).** API 응답 원문을 `data/raw/` 에 그대로
보관한다. 점수 공식을 바꿔도 **재수집 없이 과거 데이터로 재계산**된다.
테스트 fixture 로도 그대로 쓴다.

**원칙 3 — LLM 은 provider-agnostic.** `.env` 값 하나로 Gemini <-> Anthropic
을 바꿀 수 있어야 한다. 무료 티어 정책이 변하거나 비용 판단이 바뀌어도
어댑터 교체로 끝난다.

**모델 별칭(`*-latest`)을 쓰지 않는다.** 실측에서 `gemini-flash-latest` 가
HTTP 503(과부하)을 반환했다. 버전을 고정하고 `modelVersion` 에 기록해
프롬프트 개선 시 재처리 대상을 식별한다.

## 7. 필터링 — 4개 축

성격이 다른 것을 같은 태그 목록에 섞으면 필터와 UI가 금방 엉킨다.
축으로 분리한다.

```
축 1  성격 태그   왜 가는가       중복 허용, 배지로 표시
축 2  메뉴 레벨   무엇을 먹는가   단일값 (포함관계 있음)
축 3  주차 등급   갈 수 있는가    게이트 (탈락시킴)
축 4  실용 정보   판단 재료       표시 전용, 필터 아님
```

### 7.1 축 1 — 성격 태그 (8종, 중복 허용)

| 태그 | 판정 조건 |
|---|---|
| 대형 베이커리 | `scale=대형` AND `has_bakery` |
| 대형 카페 | `scale=대형` |
| 브런치 카페 | `menu_level=3` AND 브런치 메뉴 존재 |
| 뷰 맛집 | `view_strength >= 3` (소형이면 4, **뷰 종류가 '도심' 뿐이면 +1**) |
| 정원·마당형 | 야외 정원·산책로·잔디 존재 |
| 창고형·인더스트리얼 | 폐공장·창고 리모델링, 높은 층고 |
| 전시·복합문화 | 갤러리·전시·서점·편집숍 병설 |
| 디저트 특화 | 케이크·타르트·젤라토 전문 AND `buzz_volume >= 2.0` |

**8개에서 멈춘다.** 태그가 10개를 넘으면 의미가 사라진다.
루프탑은 뷰 맛집의 하위 속성으로, 바다뷰/강뷰/산뷰는 `view_types` 필드로
내려서 태그 폭발을 막았다.

### 7.2 축 2 — 메뉴 레벨 (단일값 1~3)

포함관계가 있으므로 태그가 아니라 단계다.

| 레벨 | 구성 | 의사결정에 미치는 영향 |
|---|---|---|
| Lv1 음료 위주 | 커피·차·에이드, 쿠키 정도 | 밥 먹고 가야 함. 체류 1시간 남짓 |
| Lv2 + 베이커리 | 빵·케이크 제대로 갖춤 | 간단히 때움. 빵 사 올 수 있음 |
| Lv3 + 식사 | 파스타·피자·플레이트 | **거기서 점심 해결.** 일정 전체가 달라짐 |

이 값이 **방문 시간대를 결정한다.** Lv3이면 11시 출발해 점심까지,
Lv1이면 점심 먹고 2시 출발. 같은 목록이라도 완전히 다른 주말이다.

**Lv1은 4인 가족에게 감점 요소**로 취급한다 (스코어링 참조).

세부 필드: `bread_baked_onsite`, `signature_menu`, `meal_types[]`

### 7.3 축 3 — 주차 등급 (게이트)

차량 이동 가족에게 주차 불가는 다른 장점을 전부 무효화한다.
따라서 태그가 아니라 **탈락시키는 게이트**다.

| 등급 | 상태 | 처리 |
|---|---|---|
| A | 전용 주차장 넉넉 (10대 이상·"넓다"·발렛) | 기본 노출 |
| B | 전용이나 협소(5~9대), **또는 건물·상가 공용 주차장** | 기본 노출 + "주말 대기" 경고 |
| C | 5대 미만, 인근 유료·공영 의존, "주말엔 자리 없다" | **기본 숨김.** "서울 도심 보기" 토글에서만 |
| D | 주차 불가·극난 | 완전 제외 |
| ? | 정보 없음 | 노출하되 "주차 미확인" 배지 |

**v3.1 정정 (2026-08-20, 200곳 실측).** LLM 이 조건부 무료를 A 로 올리고
있었다 — 테라로사 광화문 "1만원 이상 1시간 무료", 넬보스코 "1시간 무료",
피그먼츠 "주말 2시간 무료" 가 전부 A 였다. **"1시간 무료", "주문 금액 이상
무료", "주말만 무료" 는 최대 B 다.** 무료 시간이 있다는 것이 넉넉하다는
뜻이 아니다. 토요일 오후 도심 건물 주차장의 1시간 무료는 만차다. 그리고
"매장 앞 1대" 는 협소가 아니라 사실상 불가이므로 C 다. 근거는
`2026-08-20-full-scan-findings.md` 발견 D.

**추출 트릭:** 한국 블로거는 주차 얘기를 거의 반드시 쓴다. 블로그 검색을
`"{시군구} {상호} 주차"` 로 **한 번 더 따로 던져** 주차 언급 스니펫만
집중 수집한다. 카페당 호출 1회 추가지만 등급 정확도가 크게 오른다.
`parking_evidence` 인용을 필수로 강제한다.

### 7.5 소형 카페 처리 — "작을수록 더 압도적이어야 통과"

"동네 카페"의 반대말은 *작은 카페*가 아니라 *일부러 갈 이유가 없는 카페*다.
규모는 여러 이유 중 하나일 뿐이므로 소형도 통과 가능하게 한다.
단, 그냥 열어두면 20석 동네 카페가 뷰 태그 하나로 밀려 들어온다.

```
좌석 60석 미만이면 태그 임계값 상향
   뷰 맛집       view_strength >= 4   (기본 3)
   디저트 특화    buzz_volume >= 2.5   (기본 2.0)
   창고형         층고·규모 근거 필수
```

그리고 **좌석 규모를 카드 최상단에 크게 표시**해 최종 판단을 사람에게 넘긴다.

### 7.6 5단 필터 퍼널

```
Layer 0  수집          그물 A·B·C, kakao_place_id 중복 제거
Layer 1  하드 배제      규칙 기반, LLM 미사용
Layer 2  화제량 컷      동네 카페 대량 탈락
Layer 3  LLM 속성 추출  Layer 2 통과분만
Layer 4  판정          태그·메뉴레벨·주차등급 부여
Layer 5  최종 게이트    노출 여부 결정
```

#### Layer 1 — 하드 배제 (규칙)

```
프랜차이즈 블랙리스트
  스타벅스 투썸 이디야 메가 컴포즈 빽다방 커피빈 할리스
  파스쿠찌 탐앤탐스 더벤티 매머드 / 파리바게뜨 뚜레쥬르 던킨

카테고리 배제
  테마카페 > 스터디 · 만화/보드 · 애견 · 키즈 · 룸
  커피전문점 > 무인 · 테이크아웃

상호 패턴 배제 — 폐기 (2026-08-19 정정)
  "OO점" 지점 접미사 규칙은 사용하지 않는다. 테라로사 서종점·
  앤트러사이트 서교점처럼 우리가 가장 원하는 대형 지점을 잘라낸다.
  명시적 블랙리스트만 사용한다.
```

블랙리스트는 **DB 테이블로 관리**한다. 코드에 하드코딩하면 신규
프랜차이즈가 생길 때마다 배포가 필요하다.

#### Layer 2 — 화제량 컷 (v3: 문서를 직접 검증한다)

동네 카페와 대형 카페를 가르는 신호는 **"얼마나 자주 글이 올라오는가"** 다.
대형 카페는 일부러 찾아가는 곳이라 후기를 쓴다. 동네 카페는 그냥 간다.

**v2 의 `log10(total_posts)` 방식은 폐기했다.** 다음 검색의 `total_count` 는
OR 매칭 집계라서 지역명·일반어에 지배된다. 실측:

| 검색어 | total_count |
|---|---|
| 양평 테라로사 | 22,607 |
| 파주 더티트렁크 | 25,838 |
| **망리단길없는카페이름12345** (존재하지 않음) | **3,434** |

**존재하지 않는 카페도 3,434건을 받는다.** 집계를 믿을 수 없다.
따옴표 구문 검색도 무시된다. 대신 문서를 직접 검증한다.

```
1) query     = "{시군구} {상호}", sort=recency, size=50
2) relevant  = 받은 50건 중 다음 둘을 모두 만족하는 문서
                 - 제목·본문에 상호명 포함
                 - 카페 문맥어 하나 이상 포함
                   (카페 / 베이커리 / 커피 / 빵 / 디저트 / 브런치)
3) precision   = relevant.length / 받은 문서 수
4) span_days   = relevant 최신일 - relevant 최고일
5) posts_per30 = relevant.length * 30 / max(span_days, 1)
```

컷 (초기값. 13.1절 골든셋으로 보정한다):

```
precision   < 0.30  -> 탈락   상호가 실재하지 않거나 검색으로 식별 불가
posts_per30 < 8     -> 탈락   월 8건 미만은 동네 카페
```

실측 기준값 (2026-08-20 구현 시 재측정):

| 카페 | 상호명만 | **문맥어 조건 적용** | posts_per30 | 판정 |
|---|---|---|---|---|
| 테라로사 (양평) | 96% | **70%** | 86 | 통과 |
| 존재안함카페 | 0% | **0%** | 0 | 탈락 |

**문맥어 조건이 정밀도를 26%p 낮춘다. 이것이 의도한 동작이다.** 테라로사
검색 결과 50건 중 상호명을 포함한 48건을 하나씩 확인한 결과, 탈락한 13건은
거의 전부 **카페 후기가 아니라 이름만 스친 글**이었다:

```
· 23개월 아기랑 갈만한 곳 BEST 3      여행 큐레이션에 이름만
· 양평 맛집 토담골 곤드레돌솥정식      한식당 후기
· 리버뷰 디엠버호텔                   호텔 후기 ("인근에 테라로사")
· Gardening 입문기 - 삼봉아양농장      농장 일기
· 블랙밤부 푸팟퐁커리                 태국음식점 후기
· 테라아트랜드 양평독채스테이          숙소 후기
· 30개월 아들 어린이집 여름방학        일상 일기
```

이 "지나가는 언급"들이 바로 일반명사 상호의 점수를 부풀리는 노이즈다.
따라서 **진짜 카페의 현실적 정밀도 상한은 약 0.8** 이고, 컷 0.30 과의
여유가 충분하다. 정밀도를 HotScore 승수로 쓸 때 실존 카페가 약 0.7배로
일괄 축소되지만 상대 순위는 보존된다.

문맥어 확장 후보(`아메리카노` `라떼` `로스터리` 등)를 검토했으나 13건 중
구제되는 것은 `차` 로 3건뿐이었고, `차` 는 주차·자동차·차례에 걸려
오염을 되불러온다. 확장하지 않는다.

**일반명사 상호 방어 (필수).** `수목원` 은 precision 100%, 월 634건으로
나왔지만 카페 글이 아니라 "가평 수목원" 전반이다. 2)의 카페 문맥어 동시
출현이 1차 방어이고, 추가로:

- 상호명이 2글자 이하이거나 일반명사 사전에 걸리면 `ambiguousName = true`
  로 표시하고 **골든셋 경계 구간으로 강제 편입**한다 (사람이 반드시 본다)
- `posts_per30 > 300` 은 과다다. 일반명사 오염으로 의심해 플래그한다

**신규 오픈 구제.** `relevant` 최고일이 180일 이내면 `posts_per30` 컷을
면제하고 가속도로만 평가한다. 없으면 갓 오픈한 대형카페가 전부 탈락한다.

#### Layer 3 — LLM 속성 추출

입력: 블로그 스니펫 상위 15개 + 주차 전용 스니펫 5개 + 카카오 메타
출력: `cafe_attributes` 스키마 (JSON, 구조화 출력 강제)

**`evidence` 와 `parking_evidence` 인용을 필수 필드로 강제한다.**
근거를 못 대면 환각이다. 사람이 검수할 때도 이 한 줄이면 3초에 판단된다.

`model_version` 을 함께 저장해 프롬프트 개선 시 재처리 대상을 식별한다.

#### Layer 5 — 최종 게이트

```
태그 0개    -> 제외   "동네 카페"
주차 D      -> 제외   "차로 못 감"
주차 C      -> 도심 모드에서만
그 외       -> 통과
```

**"동네 카페 = 태그 0개"** 가 조작적 정의다. 별도 동네카페 판별기를
만들지 않는다. 넣고 싶은 것의 정의를 명확히 하면 뺄 것은 자동으로
정의되며, 5번째·9번째 태그를 추가해도 배제 규칙을 고칠 일이 없다.

### 7.7 사람 검수 루프 (CLI)

자동 판정을 과신하지 않는다. 4명이 쓰는 서비스에서 오탐 스무 개를 잡겠다고
알고리즘을 깎느니 손으로 스무 번 고치는 것이 압도적으로 빠르다.

웹이 아니라 **CLI에서 한다** (10절). 아빠만 쓰는 도구다.

```
npm run hide <cafe>        동네카페 오통과 -> 즉시 숨김
npm run hide --list        숨긴 곳 조회
npm run hide --restore     오탈락 복구
npm run inspect <cafe>     판정 근거 전체 출력 (evidence 포함)
```

모든 액션은 `moderation_actions` 에 쌓여 프롬프트 개선 데이터가 된다.
13.1절의 골든셋 라벨링과 같은 판정 흐름을 공유한다.

## 8. 스코어링 (v3)

### 8.1 HotScore — 지금 뜨는가 (0~100)

핫함의 실체는 절대량이 아니라 **가속도**다. 오래된 유명 카페는 발행률이
높지만 가속도가 낮아 자연히 내려간다.

```
relevant     = Layer 2 가 검증한 관련 문서 (최대 50건, 날짜 내림차순)
posts_30d    = relevant 중 최근 30일 문서 수
posts_prev   = relevant 중 31~90일 문서 수
baseline_30  = posts_prev / 2
acceleration = (posts_30d + 3) / (baseline_30 + 3)      # 라플라스 스무딩

posts_per30  = Layer 2 산출 발행률
volume       = clamp(log10(posts_per30 + 1) / 2.3, 0, 1) # 월 200건이면 1.0
precision    = Layer 2 산출 정밀도
freshness    = 1 / (1 + days_since_latest / 30)
novelty      = 첫 관련글 180일내 1.0 / 365일내 0.5 / 그 외 0.0

HotScore = 100 * precision * (
    0.45 * clamp(log2(acceleration) / 2, 0, 1)   # 4배 급증이면 만점
  + 0.30 * volume
  + 0.15 * freshness
  + 0.10 * novelty
)
```

가속도 가중 0.45가 이 서비스의 성격을 정의한다.

**`precision` 을 전체에 승수로 곱하는 것이 v3 의 핵심 변경이다.** 검색으로
식별되지 않는 카페는 다른 지표가 아무리 좋아도 점수가 내려간다. 동명이인
오염과 일반명사 오염이 여기서 자동으로 감쇠한다. v2 처럼 컷으로만 처리하면
경계선 바로 위의 오염된 카페가 만점을 받는다.

**50건 창의 한계가 오히려 장점인 이유.** 절대 집계를 못 쓰는 대신 발행
밀도를 직접 재는데, 50건이 2.4일에 걸치면 월 634건, 18.7일이면 월 69건이다.
**약 200배의 동적 범위**가 실측으로 확인됐다. 해상도가 충분하다.

### 8.2 FamilyFit — 우리가 갈 만한가 (0~1 승수)

```
distance_decay = exp(-drive_minutes / 70)      # 70분에서 약 0.37
   1차 범위에서는 직선거리 x 1.35 로 근사. 확정 후보만 나중에 실측

parking_mult   = A 1.0 / B 0.85 / C 0.40 / D 0.0 / ? 0.70
menu_mult      = Lv3 1.0 / Lv2 0.95 / Lv1 0.75
unvisited_mult = 미방문 1.0 / 6개월내 0.15 / 1년내 0.50 / 그 외 0.80
season_mult    = 야외 위주 x 여름(7-8월)·겨울(12-2월) 0.5
                 야외 위주 x 봄·가을 1.2 / 그 외 1.0
teen_mult      = 0.85 + 0.03 * teen_appeal      # 0.85 ~ 1.00

FamilyFit = distance_decay * parking_mult * menu_mult
          * unvisited_mult * season_mult * teen_mult
```

`unvisited_mult` 의 6개월내 0.15가 중요하다. 최근 다녀온 곳이 추천 상단을
계속 차지하면 서비스가 무의미해진다. 완전히 0으로 두지 않는 이유는
"거기 또 가고 싶다"를 허용하기 위함이다. 이 승수는 3절 ⑤의 "다녀왔어요"
토글에서 나오는 `visits` 데이터로만 동작한다.

### 8.3 취향 학습 — 범위에서 제외 (v2)

v1에 있던 태그별 평점 학습(`taste_mult`)을 **제거했다.**

평점 입력이 없으므로 학습할 신호가 없다. 되살리려면 구성원별 평점 UI,
프로필 식별, 평점 테이블이 다시 필요해지고 이는 v2의 유지보수 최소화
목표와 정면으로 충돌한다.

**대체 근거:** HotScore(화제성) x 거리 x 주차 x 메뉴레벨 x 미방문만으로도
후보 10곳은 충분히 좁혀진다. 4명 가족의 표본으로 학습한 승수는 애초에
신뢰 구간이 넓어 효과가 의심스러웠다. 넣지 않는 것이 옳다.

### 8.4 최종

```
FinalScore = HotScore * FamilyFit
```

주말 후보는 FinalScore 상위에서 뽑되 **태그 다양성 제약**을 건다.
상위 3곳이 전부 "정원·마당형"이면 리스트의 의미가 없으므로, 3곳의 성격
태그가 최소 2종 이상 서로 다르도록 강제한다.

## 9. 데이터 저장 — JSON in git (v3)

**DB를 쓰지 않는다.** v2 개정으로 쓰기 기능이 "다녀왔어요" 하나로 줄고
그것마저 CLI 로 옮기면서 (10절) DB 의 존재 이유가 사라졌다.

카페 1,500곳 = 약 1.5MB. git 에 아무 부담이 없고 전부 메모리에 올려
필터링된다. **복잡한 쿼리가 하나도 없는데 Postgres 를 쓸 이유가 없다.**

### 동작 방식

```
GitHub Actions 배치  ->  data/*.json 갱신 후 자동 커밋
                              |
                     Vercel 자동 재배포 -> 정적 HTML
                              |
                     가족은 그냥 읽는다 (서버 없음)
```

### 파일 구조

```
data/

    YYYY-MM-DD/*.json 원본 응답 스냅샷 (재계산·fixture)
```

### 스키마는 zod 가 단일 진실 원천

`src/schema.ts` 의 zod 스키마가 **타입과 런타임 검증을 동시에** 담당한다.
읽을 때마다 `parse` 하므로 손으로 편집한 JSON 이 깨져도 즉시 잡힌다.
SQL DDL 과 TypeScript 타입을 따로 관리하며 어긋나는 문제가 사라진다.

### git 운영 규칙

- 데이터 커밋은 **`data:` 프리픽스**로 코드 커밋과 구분한다
- 배치가 자동 커밋하며 메시지에 변경 요약을 담는다 (신규 N곳, 갱신 M곳)
- **`data/raw/` 는 git 에 커밋하지 않는다** (`data/.gitignore`). 실측 결과
  카카오 블로그 응답 1건이 **36 KB** 이고 카페 1,500곳이면 **하루 53 MB**,
  90일이면 **4.7 GB** 다. git 에 넣을 수 없는 규모다 (2026-08-20 실측 정정)
- 그래서 `raw/` 의 용도는 **당일 디버깅과 fixture 캡처**다. 테스트용
  fixture 는 `raw/` 에서 골라 `tests/fixtures/` 로 복사해 커밋한다
- **점수 공식을 바꿔 재계산할 때는 재수집한다.** 하루치 1,500 호출이면
  되고 쿼터에 여유가 있으므로 비용이 실질적으로 없다. "재수집 없이
  재계산"은 당일 로컬에서만 성립한다
- **`buzz.json` 은 카페별 최신 1건만 보관한다** (2026-08-20 정정).
  180일 롤링으로 정했으나 실제 발굴 결과가 **6,216곳**(전제는 1,500곳)이라
  스냅샷 400B x 5,866 x 180일 = **약 403 MB 를 한 파일에 담고 매일 커밋**하게
  된다. 게다가 그 이력을 읽는 코드가 없다 — 가속도는 `computeBuzz` 가 방금
  받은 50건 창에서 계산하고 `classify`·`weekly-suggest` 는 최신 1건만 조회한다.
  순수한 비용이므로 최신 1건만 남긴다 (약 2.2 MB, 크기 고정).
  추이 그래프가 필요해지면 월 1건 집계 파일을 따로 둔다

### 웹 화면 4개 — 쓰기는 두 파일에만

| 화면 | 내용 | 쓰기 |
|---|---|---|
| **이번 주** (홈) | 추천 **10곳** 카드 + 다음 10곳 페이지. 카카오톡 링크의 도착지 | 없음 |

| **다녀온 곳** | 방문 기록 + 가족 별점·후기. 최근순 | 방문 취소 |

> **v3.3 정정 (2026-08-21).** "쓰기 엔드포인트 0개" 를 되돌렸다. 근거는
> 10.3절에 적었다. 쓰기 대상은 `reviews.json` · `visits.json` 두 파일뿐이며
> 화면은 여전히 전부 빌드 타임 생성이다.

```
npm run visited <카페>     월 2회, 아빠가 실행
```

> **v3.2 정정 (2026-08-20).** 추천을 3곳에서 **10곳**으로 늘렸다. 사용자
> 피드백이 "3개는 너무 적다" 였고, 4인 가족이 취향을 맞추려면 고를 폭이
> 필요하다. 10곳 안에서 못 고르면 **다음 10곳**으로 넘어간다.
>
> 무한 스크롤은 쓰지 않는다 — 어디까지 봤는지 알 수 없고 되돌아오면 맨 위로
> 튄다. 페이지 번호가 있으면 "3페이지까지 봤다" 가 성립하고, 가족이 대화하며
> 보는 목록이므로 위치를 말할 수 있어야 한다.
>
> 카카오톡 200자에는 10곳이 들어가지 않으므로 **이름 3곳 + "외 7곳"** 으로
> 줄인다. 메시지의 목적은 정보 전달이 아니라 앱을 열게 하는 것이다.

**카드 상단 고정 3종:** `규모(대형/중형/소형)` · `주차 등급` · `메뉴 레벨`
갈지 말지를 3초에 결정하게 하는 정보다.

> **v3.1 정정.** 원래 `좌석 규모` 였다. 실측에서 `seatsEstimate` 는 28/28 이
> null 이고 `scale` 은 채워졌다 — 블로거는 좌석 수를 거의 쓰지 않는다.
> LLM 이 "추측하지 마라"를 지킨 결과이므로 프롬프트가 아니라 화면을 고친다.
> `scale` 마저 null 이면 "규모 미확인" 으로 띄운다.

태그는 필터가 아니라 **배지로만** 표시한다 (전체 리스트 화면에서만 칩으로
좁히기를 제공). 칩 8개를 홈에 늘어놓으면 아무도 쓰지 않는다.

### 지도를 만들지 않는다 — 외부 지도로 넘긴다

지도 SDK 는 키 관리·렌더링·모바일 제스처·버전 업데이트로 계속 손이 간다.
직접 만들지 않고 링크로 넘긴다. 그리고 이것이 **실제로 더 유용하다** —
길찾기와 리뷰·사진·메뉴판까지 이어진다.

| 링크 | 형태 | 위치 | 안정성 |
|---|---|---|---|
| **네이버지도** (주) | `https://map.naver.com/p/search/{인코딩된 "시군구 상호"}` | 카드·상세 주 버튼 | 웹 URL 패턴 의존 |
| **카카오맵** (보조) | `placeUrl` (API 응답 필드 그대로) | 상세 하단 1줄 | 높음. API가 준 값 |

네이버지도를 주 링크로 두는 이유는 **한국에서 장소 정보(리뷰·사진·메뉴판·
영업시간)가 압도적으로 풍부**하기 때문이다. 카카오맵 링크를 보조로 남기는
이유는 **하나가 깨져도 다른 하나가 동작**하게 하기 위함이며, 비용은
마크업 한 줄이다.

### 운영 도구는 전부 CLI (웹 화면을 만들지 않는다)

아빠만 쓰는 도구를 웹으로 만들 이유가 없다. 화면·라우팅·인증이 전부 절약된다.

```
npm run visited    "다녀왔어요" 기록 (v3에서 웹 -> CLI 이동)
npm run label      골든셋 O/X 판정 (13.1절)
npm run health     소스 상태 조회
npm run hide       카페 숨기기 / 복구
npm run inspect    카페 1곳의 판정 근거 전체 출력 (evidence 포함)
npm run blacklist  프랜차이즈 블랙리스트 편집
```

### 인증 — 없다 (v3.4)

접근 코드를 걷어냈다. 내용이 **카페 추천 목록**이고 개인정보가 없다.
가족 4명에게 코드를 알려주고 "코드 뭐야?" 를 응대하는 비용이, 지키는 것의
가치보다 크다는 판단이다.

`robots.txt` 로 색인은 계속 차단한다.

**알고 있는 리스크:** 주소는 완전한 비밀이 아니다. HTTPS 인증서 발급 기록
(Certificate Transparency)이 공개이므로 `*.vercel.app` 호스트명은 조회
가능하다. 따라서 **쓰기(별점·후기)가 열려 있다** — 봇이 장난 후기를 남길 수
있다. 확률은 낮고 생기면 지우면 되지만, 실제로 발생하면 **읽기는 열고 쓰기만
막는** 방식으로 바꾼다 (가족은 조작 없이, 봇만 차단).

저장 대상이 `reviews.json`·`visits.json` 두 파일로 못박혀 있어 그 이상의
피해 경로는 없다. 그 안에서도 **목록에 있는 카페만** 받는다 (`byId` 검사) —
아무 문자열이나 카페 id 로 받으면 화면에 보이지 않는 데이터가 쌓이고, 보이지
않으니 화면에서 지울 방법도 없다. 취소·삭제 방향은 검사하지 않는다: 게이트에서
빠진 카페의 기록도 되돌릴 수 있어야 한다.

### 10.3 별점·후기 — 가족 누구나 (v3.3)

v2 에서 투표·평점을 걷어냈고 v3 에서는 "다녀왔어요" 까지 CLI 로 뺐다.
**그 결정을 되돌린다.** 사용자 요청이 명확했고("링크를 통해 접속한 모두가
별점과 후기 평가할 수 있도록"), 되돌릴 값도 충분하다 — 다녀온 기록과 별점이
쌓이면 그것이 우리 가족 취향 데이터가 되고, 추천이 그것을 반영할 수 있다.

| 기능 | 누가 | 무엇 |
|---|---|---|
| 다녀왔어요 체크 | 링크로 들어온 누구나 | 같은 날 다시 누르면 취소 |
| 별점 | 링크로 들어온 누구나 | **0.5 ~ 5.0, 반개 단위** |
| 한 줄 후기 | 링크로 들어온 누구나 | 100자 |

**누가 눌렀는지 남기지 않는다.** 4명이 쓰는 페이지에서 그것을 알려면 인증을
붙여야 하고, 인증을 붙이면 아무도 쓰지 않는다. 별명만 받고 그 별명은 각자
폰이 기억한다(localStorage) — 매번 적게 하면 역시 아무도 쓰지 않는다.

#### 저장소는 GitHub 다. DB 를 두지 않는다

| | Supabase | **GitHub Contents API** |
|---|---|---|
| 무료 지속성 | **7일 미사용 시 프로젝트 정지** | 정지 개념이 없음 |
| 계정·대시보드 | 하나 늘어남 | 늘지 않음 |
| 백업·이력 | 별도 설정 | git 이 곧 백업 |
| 반영 속도 | 즉시 | 누른 사람 즉시 / 다른 가족 30초 |

**Supabase 를 쓰지 않는 이유가 결정적이다.** 이 앱은 월 2회 쓴다. 즉 대부분의
시간이 미사용이므로 무료 티어의 7일 정지 규칙과 정면으로 어긋난다 — 금요일에
별점을 누르려는 순간 정지 화면을 만나고, 사람이 대시보드에서 복구해야 한다.
"운영이 쉽고 무료로 평생" 이라는 요구를 만족하지 못한다.

데이터가 이미 전부 git 에 있으니 별점도 같은 곳에 둔다. 동시 수정은 `sha`
불일치(409)로 감지해 다시 읽어 합친다 — 트랜잭션 대신이며, 두 사람이 동시에
남겨도 나중 쓰기가 앞선 것을 지우지 않는다.

`GITHUB_TOKEN` 이 없으면 로컬 파일로 폴백한다. 토큰을 만들기 전에도
`npm run dev` 로 실제로 눌러보며 확인할 수 있다.

#### 반개 별점의 타겟 크기

별 하나를 좌·우 두 구역으로 나눈다. 별을 **44px** 로 잡아 각 구역이 22px 이
되게 했다. 이보다 작으면 모바일에서 반개를 겨냥할 수 없다 (스펙 10.1 의
44px 규칙은 별 전체 높이로 지킨다).

### 10.4 대표 이미지 (v3.4)

목록이 텍스트만이면 밋밋하다. 아내분은 인스타에서 카페를 찾는 사람이므로
사진이 판단의 큰 부분이다.

**추가 API 호출이 0이다.** 카카오 블로그 검색 응답에 `thumbnail` 필드가
이미 들어 있고, 화제량 수집이 카페마다 그 응답을 받는다. 거기서 함께 얻는다.

```
실측: 판정 통과 298곳 전부 이미지 확보 (이번 주 10곳 10/10)
      블로그 문서 50건 중 썸네일 보유 21건 — 한 곳당 최소 1장은 나온다
```

| 규칙 | 이유 |
|---|---|
| **관련성 통과 문서에서만 고른다** | 엉뚱한 사진 한 장은 텍스트 오류보다 신뢰를 더 깎는다 |
| **60px 정사각으로만 쓴다** | 카카오 썸네일이 130x130 이다. 카드 상단 큰 사진으로 늘리면 뭉개진다 |
| **매일 갱신한다** | CDN URL 이 영구 보장이 아니다. 깨져도 다음날 회복된다 |
| **없으면 자리표시자** | 이미지가 없다고 카드가 무너지지 않는다 |
| **active 카페를 먼저 수집** | `--limit` 으로 잘릴 때 추천에 뜨는 곳이 비어 보이면 안 된다 (실측: 처음엔 10곳 중 0곳이었다) |

네이버지도 첫 이미지는 쓰지 않는다 — HTML 파싱이 필요하고 그것이 스펙 6.1 이
금지한 것이다. 카카오 이미지 검색 API 는 호출이 늘고 관련성이 오히려 낮다.

| 이번 주 추천에서 **제외** | 6개월. 점수 감점(0.15배)만으로는 목록에 남아 "또 거기?" 가 된다 |
| 전체 리스트에는 남는다 | 또 가고 싶은 곳을 찾을 수 있어야 한다 |
| 취소는 **최근 1건만** 지운다 | 전부 지우면 작년 기록까지 사라진다 |
| 취소하면 추천에 **다시 올라온다** | 잘못 누른 것을 되돌릴 수 있어야 사람이 누른다 |
| 목록에 별점·후기·날짜 | 다녀온 뒤의 기억이 여기 쌓인다. 최근이 위 |

**빌드 시점 필터만으로는 부족하다.** 체크하고 홈에 돌아오면 그 카페가 그대로
1위에 남는다 (페이로드는 빌드 시점 값이다). 홈이 `/api/visited` 를 읽어
실시간으로도 걸러낸다.

`add`/`remove` 를 명시적으로 받는다. 토글로 두면 "같은 날" 만 취소되어,
어제 잘못 누른 것을 오늘 취소하면 오늘 방문이 새로 추가된다.

**실시간 기록이 진실이다 — 단, 읽기가 성공했을 때만.** 빌드 타임 목록과
`/api/visited` 는 같은 저장소(`data/visits.json`)에서 나온다. 따라서 실시간에
없다는 것은 취소되었다는 뜻이며, 합집합으로 두면 취소를 눌러도 다음 배포까지
카드가 남는다. 반대로 토큰이 없거나 GitHub 읽기가 실패해도 응답은 200 과
`visits: []` 다. 그 빈 배열을 진짜 기록으로 믿으면 **다녀온 곳 탭이 통째로 비어
보이고, 가족에게는 기록이 지워진 것으로 보인다.** 그래서 GET 은 `ok` 를 함께
내려보내고, `ok !== true` 면 화면은 빌드 타임 기록을 그대로 유지한다.

**별점·후기 읽기에도 캐시를 두지 않는다.** 30초 캐시를 뒀더니 별점을 남긴 직후
"다녀온 곳" 에 **"아직 별점이 없어요"** 가 떴다 (감사 중 실측). 남긴 사람에게 그
문구는 "저장이 안 됐다" 로 읽히고, 그러면 다시 남겨 중복이 생긴다.

**방문 기록 읽기에는 캐시를 두지 않는다.** 후기와 달리 30초 캐시가 치명적이다 —
체크한 직후 다녀온 곳이 비어 보이고 이번 주 추천에도 그대로 남아, 누른 것이
안 눌린 것처럼 보인다 (실측). 월 몇 번 열리는 페이지이므로 매번 읽어도 GitHub
한도(5,000/시간)에 닿지 않는다. 후기는 자기 것이 즉시 보이므로 30초를 유지한다.

### 10.6 방향 묶음 — "어느 쪽으로 갈까" (v3.6)

전체 리스트를 행정구역으로 모아 보고 싶다는 요청에서 시작했다. 그런데 실측
분포가 시군구 칩을 막았다.

```
표시 대상 210곳이 43개 시군구에 흩어져 있다
그중 17개 시군구는 1~2곳뿐        <- 칩 절반이 카드 한 장을 위한 칩
10곳 이상인 곳은 6개
```

칩 43개는 375px 화면에서 세 줄을 먹는다 (10.1 이 가로 스크롤을 금지한다).
그래서 **방향 6개로 묶고, 방향을 고르면 그 안에서 시군구별로** 보여준다.
원래 요청한 행정구역 묶음은 두 번째 층에서 충족된다.

| 방향 | 포함 | 일반 / 도심 포함 |
|---|---|---|
| 가까운 곳 | 인천·부천·시흥 | 15 / 22 |
| 서울 | 서울 전역 | 26 / 71 |
| 서쪽 | 김포·강화 | 21 / 21 |
| 북쪽 | 고양·파주·양주·의정부 | 37 / 40 |
| 동쪽 | 남양주·양평·가평·하남·광주 | 59 / 66 |
| 남쪽 | 광명·안산·수원·용인·평택 | 52 / 79 |

**차로 나가는 가족의 첫 질문이 "안성시 볼까" 가 아니라 "오늘 어느 쪽" 이다.**
부수 효과가 하나 있다 — "가까운순" 정렬이 의미를 갖는다. 지금까지는 광명 23분,
계양 25분, 김포 25분이 섞여 나왔는데 이것들은 전혀 다른 방향이다.

배정은 **명시적**이다 (`src/config/zones.ts`). 방위각으로 계산하면 강화군(북서)
이나 하남시(동남)처럼 경계에 걸린 곳이 사람 감각과 어긋난다. 65개뿐이므로 손으로
적는 편이 예측 가능하고, 빠진 시군구는 테스트가 잡는다 — 미배정은 조용히
'가까운 곳' 으로 떨어지므로 테스트가 없으면 먼 카페가 집 근처에 섞인다.

파이프라인이 `zone` 을 계산해 페이로드에 실어 보내고 웹은 필터만 한다. 기점이
바뀌면 배정도 바뀌어야 하므로, 나중에 기점 선택을 붙일 때 고칠 곳은 이 파일 하나다.

### 10.10 지역 묶음은 방향이 아니라 시 단위다 (v3.7)

10.6 의 방향 6칩을 **시 단위 32칩**으로 바꿨다. 가족이 두 주 써 보고 나온
요청이다 — "북쪽" 보다 "김포" 로 말한다.

방향으로 묶었던 이유(시군구 43개는 너무 많다)는 여전히 유효하다. 다만 두 가지가
바뀌었다.

```
경기는 이미 시 단위로 저장돼 있다 (수원시·용인시 …). 쪼갤 것이 없었다
서울(175곳)과 인천(58곳)만 하나로 묶으면  43 -> 32
```

| | 처리 | 이유 |
|---|---|---|
| 경기 | 시·군 그대로 | 이미 시 단위 |
| 서울 | 하나로, **맨 뒤** | 거의 안 간다. 칩 열 개를 줄 이유가 없다 |
| 인천 | 하나로 | 집이 부평이다. 인천 안에서 구를 가르는 것이 무의미하다 |

칩 32개는 여전히 여섯 줄이다. 그래서 **가까운 여덟 개만 펴 두고 나머지는
접는다** (`＋24개 더`). 고른 지역이 접힌 구간에 있으면 그것만 끌어올린다 —
고른 칩이 안 보이면 무엇으로 걸러진 목록인지 알 수 없다.

서울·인천을 누르면 **그 안에서 구별로** 묶는다 (`SPLIT_AREAS`). 10.6 의 두
번째 층을 그대로 재활용한다.

`zone` 은 페이로드에 남긴다 — 화면은 안 쓰지만 감사가 시도 정합성을 볼 때
쓴다 (서울 카페가 '가까운 곳' 에 섞이지 않았는가).

### 10.16 전량 렌더의 전제가 깨졌다 (v3.7)

10절은 "무한 스크롤을 만들지 않는다 — 통과분이 수백 곳이라 전량 렌더 + 칩
필터가 더 빠르고 코드도 없다" 고 적었다. **그 전제가 깨졌다.**

판정 적체를 따라잡으면서 297 -> 1,035곳이 됐고, 실측으로:

```
카드 664개 · DOM 노드 15,557개 · HTML 2.1MB · 로드 2.5초 (데스크톱 유선)
```

모바일은 이보다 훨씬 느리고, 판정 대기가 2,200곳 남아 있어 계속 커진다.

**60곳씩 끊어 그린다** (`PAGE_CHUNK`). 실측 DOM 노드 15,557 -> 1,547.
데이터는 전부 내려보내고 렌더만 자른다 — 검색과 칩이 전체를 봐야 하기
때문이다. 검색·칩으로 좁히면 대개 한 묶음 안에 들어와 버튼이 보이지 않는다.

펼친 수는 주소에 싣는다 (`?v=240`). 300곳까지 펼쳐 놓고 카페를 열었다
돌아왔을 때 60곳으로 접히면 보던 자리를 잃는다.

**조건이 바뀌면 처음부터 다시 센다.** 300곳까지 펼쳐 둔 채 지역을 바꾸면
그 지역 300곳이 한꺼번에 그려져서 방금 줄이려던 것이 돌아온다.

### 10.17 NEW 를 맨 앞에 띄우는 데에도 상한이 필요하다 (v3.7)

10.11 에서 NEW 를 정렬과 무관하게 맨 앞으로 띄웠다. 그때는 0곳이라 몰랐는데,
판정이 진행되며 54곳이 되자 **첫 화면을 통째로 먹었다.** "화제순" 을 눌러도
앞쪽 다섯 페이지가 전부 NEW 라 정렬의 의미가 사라진다.

앞으로 띄우는 것은 **최근 등록 10곳까지**(`NEW_PINNED`)다. 나머지는 제자리에
두되 배지는 그대로 붙는다. 전부 보려면 NEW 칩을 누른다.

띄운 것들끼리는 화제순이 아니라 **최근 등록순**이다 — "새로 들어온 것" 을
보여주는 자리이므로 그 안에서도 새것이 앞이다.

### 10.11 검색·NEW·주소에 실은 필터 (v3.7)

세 가지가 같은 뿌리에서 나왔다 — **목록이 297곳에서 681곳으로 늘었다.**

**검색.** 업소명만, 공백·대소문자 무시, **한 글자도 검색된다** (`콩`, `빵`
같은 한 글자 상호가 실제로 있다). 지역명은 일부러 안 넣었다 — "중" 을 치면
중구 카페가 딸려 나와 시끄럽다. 지역은 칩이 있다.

**NEW.** `firstSeenAt` 을 30일 창에 그대로 넣으면 오늘은 전부 NEW 다. 최초
대량 수집(2026-08-19~21)이 사흘 만에 6,218곳을 넣었기 때문이다. 그래서
**기준선(`SEED_UNTIL = 2026-08-22`) 이후에 발굴된 것만** NEW 로 본다. 착수
시점에 0곳이고 그것이 정직한 상태다. 감사에 `new_flood` 규칙을 뒀다 —
NEW 가 30% 를 넘으면 기준선이 어긋난 것이다.

주의: NEW 는 **"우리 목록에 새로 들어왔다"** 지 "새로 문을 열었다" 가 아니다.
개업일을 주는 무료 API 가 없다 (10.12).

**주소에 실은 필터.** 고른 칩·검색어·정렬을 `?q=&a=&t=&s=&c=&n=&o=` 로
주소에 싣는다. 목적은 하나 — 카페를 열었다 뒤로 돌아왔을 때 필터가 풀리지
않는 것. 이번 주 탭만 `?p=` 로 돼 있었고 나머지 두 탭이 빠져 있었다.

구현에서 한 번 틀렸다. `window.history.replaceState` 로 주소만 바꾸면 **되지
않는다** — 주소창은 바뀌지만 Next 라우터가 들고 있는 히스토리 항목은 그대로여서
뒤로 오면 필터 없는 `/list` 가 나온다 (실측). `router.replace` 로 라우터를
거쳐야 하고, 타자마다 왕복하지 않게 400ms 묶는다.

`push` 가 아니라 `replace` 다. 칩을 다섯 번 눌렀다고 뒤로가기를 다섯 번 눌러야
목록을 벗어나는 것은 아무도 원하지 않는다.

### 10.12 영업시간과 리뷰 수는 싣지 않는다 (v3.7)

요청받았고, **가져올 방법이 없어서 넣지 않기로 했다.** 이유를 남긴다 —
안 그러면 반년 뒤에 같은 조사를 다시 한다.

| 경로 | 결과 |
|---|---|
| 카카오 로컬 API | 상호·주소·전화·좌표만. 영업시간 필드 없음 |
| 네이버 지역검색 API | 영업시간 없음, 리뷰 수 없음 |
| 구글 Places API | 둘 다 준다. **카드 등록 필수** → "결제 없이 평생" 이 깨진다 |
| 지도 페이지 크롤링 | 처음부터 배제한 방식 (6절) |
| 블로그 글에서 LLM 추출 | 된다. 절반쯤 틀린다 |

마지막 것이 유일한 후보였는데 **틀린 영업시간은 없는 것보다 나쁘다.** 한 시간
운전해서 닫힌 문 앞에 선다. 대신 카페 화면에 `영업시간·휴무일 확인` 버튼을
네이버지도로 크게 걸었다. 한 번 눌러서 정확한 값을 본다.

리뷰 수 자리에는 **우리가 직접 센 블로그 글 수**를 넣는다 (`posts30`,
`posts90`). 여기서 하나 걸렸다 — 화면에 쓰던 `postsPer30` 은 추정 발행률
(`글수 x 30 / 관측기간`)이라 50건 창이 이틀에 차면 `월 599건` 이 나온다.
같은 카페의 90일 실측은 46건이었다. 둘을 한 줄에 놓자마자 서로를 부정했다.
**점수에는 발행률, 화면에는 실측**으로 갈랐다.

### 10.13 별점을 남기면 다녀온 것이다 (v3.7)

별점과 `다녀왔어요` 를 따로 누르게 했더니 "버튼이 왜 필요하냐" 는 말이 나왔다.
맞다 — 별점을 남겼으면 다녀온 것이다. **후기 저장 시 서버가 방문 기록도 함께
쓴다.** 화면에서 두 번 호출하지 않는 이유: 첫 요청만 성공하면 별점은 있는데
다녀온 곳에는 없는 상태가 남는다.

버튼은 남긴다. 세 가지 경우가 있다.

1. 별점 없이 다녀온 경우 (별로였거나, 점수를 미루는 경우)
2. 추천에서 6개월 내리는 유일한 스위치
3. 잘못 누른 것의 취소

대신 **별점을 위로, 버튼을 아래로** 내렸다.

### 10.14 별점 수정·삭제 (v3.7)

`PATCH` / `DELETE /api/reviews`. `createdAt` 은 그대로 두고 `updatedAt` 만
남긴다 — 고쳤다고 목록 순서가 튀어 오르면 "새 후기가 올라왔나" 로 읽힌다.

**누가 남겼는지 확인하지 않는다.** 인증이 없고(10절 인증 항목), 4명이 쓰는
화면에 로그인을 붙이면 아무도 안 쓴다. 대신 두 가지를 둔다.

- 지울 때 별명과 점수를 넣어 묻는다 (`'김' 님이 남긴 별점 4.0점을 지울까요?`)
- 이 폰에서 남긴 것에는 `내가 남김` 표시 (localStorage). 막는 것이 아니라
  알려주는 장치다

후기를 지워도 **방문 기록은 남긴다.** 별점을 지우는 것과 안 갔다는 것은 다르다.

### 10.15 열람 전용 배포 (v3.7)

동료에게 줄 주소. 같은 저장소를 Vercel 프로젝트 두 개로 띄운다.

**막는 쪽이 기본값이다.** 처음에는 열람용에 `NEXT_PUBLIC_VIEW_ONLY=1` 을 넣어
막으려 했는데, 그 변수를 빠뜨리면 조용히 쓰기가 열린다 — 실패했을 때 위험한
쪽으로 넘어지는 설계다. 그래서 뒤집었다.

```
쓰기는 host 가 `cafe-recommender` 로 시작할 때만 허용한다 (그리고 localhost)
```

새로 띄운 배포는 이름이 무엇이든 **자동으로 열람 전용**이 된다. 열람용
프로젝트 이름을 잘못 지어도 안전하다.

| 겹 | 무엇 | 뚫리면 |
|---|---|---|
| 화면 | `NEXT_PUBLIC_VIEW_ONLY` (next.config 가 프로젝트 이름으로 판단) | 개발자도구로 뚫린다 |
| **서버** | 요청의 `host` 를 보고 403 | **여기가 실제 방어선** |
| 저장소 | 읽기 전용 토큰 또는 토큰 없음 (선택) | — |

화면은 API 응답의 `writable` 로 자기를 바로잡는다. 이름을 규칙과 다르게 지어
버튼이 보이더라도, 첫 응답이 오면 사라진다.

**읽기는 살린다** — 가족이 남긴 별점과 후기가 보여야 목록이 쓸모 있다. 그래서
저장소 인터페이스를 `enabled`(붙어 있나)와 `writable`(써도 되나)로 갈랐고,
페이로드에 **빌드 시점 후기**를 카페당 10건까지 실었다. 열람용에 토큰을 아예
주지 않아도 별점이 보인다. 토큰을 주면 실시간 값이 그것을 덮는다.

여기서 한 번 틀렸다. 토큰이 없을 때 `GET /api/reviews` 가 `ok: true` 에 빈
배열을 주고 있었다 — 화면이 그것을 "후기 없음" 으로 믿고 빌드 사본을 지운다.
저장소가 안 붙어 있으면 `ok: false` 로 말해야 한다 (다녀왔어요 쪽은 원래
그랬다).

주소를 아는 사람은 누구나 본다 (인증 없음). 가족 별점과 한 줄 후기가 보인다는
뜻이다.

### 10.7 같은 카페가 두 번 등록된 경우 (v3.6)

1차 검증에서 목록에 `비루개` 가 두 번 나왔다. 카카오에 **같은 카페가 두 개의
장소 id** 로 올라와 있고 하나는 도로명 주소가 없는 빈 껍데기였다 (`터프이너프
로스터스` 도 같은 상태). 297곳 중 2건이지만, 이번 주 추천 10칸 중 두 칸을 같은
카페가 먹을 수 있다.

`이름 + 시군구` 로 묶어 하나만 남긴다. 우리 상호에는 지점명이 붙어 있어
(`경성빵공장 남한산성점`, `배다골베이커리 포레`) 서로 다른 지점이 같은 키가
되지 않는다. 좌표 근접으로 묶는 방법도 있지만 같은 건물의 다른 카페를 잘못
합칠 위험이 더 크다.

남길 것을 고르는 순서: **도로명 주소가 있는 쪽 → 종합점수 높은 쪽 → id 작은 쪽**
(마지막은 빌드마다 결과가 흔들리지 않게 하는 결정론 장치다).

### 10.8 시군구는 "검색한 지역" 이 아니라 주소다 (v3.6)

2차 검증에서 `테라스` 의 시군구가 `중구` 인데 주소는 종로구였다. 원인은
`sigungu` 에 **검색한 지역**이 들어가 있었다는 것이다. 카카오 키워드 검색
`경기 양평군 대형카페` 는 경계 너머 남양주·광주의 카페도 함께 준다.

```
실측: active 299곳 중 20곳(6.7%) 불일치, 전체 6,218곳 중 1,669곳(27%)
```

세 곳이 어긋났다.

| 어긋난 곳 | 증상 |
|---|---|
| 카드 표기 | "양평군 · 61분" 인데 실제로는 남양주시 |
| 네이버 지도 링크 | `양평군 라온숨` 으로 검색 — 엉뚱한 결과 |
| 지역 묶음 (10.6) | 양평군 그룹에 남양주 카페가 섞임 |

주소를 진실로 삼는다 (`src/pipeline/district.ts`). 주소가 없으면 검색 지역을
그대로 쓴다. 과거 데이터는 `npm run normalize` 로 맞춘다 — 멱등이라 여러 번
돌려도 되고, 새로 발굴되는 카페는 `toCafe` 가 처리한다.

**부수 소득: 인천 행정구역 개편을 발견했다.** 주소에 `서해구` 89곳, `제물포구`
44곳, `영종구` 23곳, `검단구` 16곳이 있었다. `REGIONS` 에 없던 이름이라 방향
묶음에서 조용히 기본값('가까운 곳')으로 떨어질 상태였다. 네 곳을 추가했고,
옛 이름(중구·동구·서구)도 남겼다 — 카카오가 아직 옛 주소를 주는 곳이 있고
같은 카페는 장소 id 로 걸러진다.

> 지역 매칭을 시도(sido)로만 하기로 한 과거 결정이 여기서 값을 했다. 시군구로
> 검사했다면 이 카페들이 "타지역" 으로 조용히 버려졌을 것이다.

### 10.9 한 주 추천에 같은 지역은 2곳까지 (v3.6)

검증에서 10곳 중 고양시가 3곳이었고, 그중 둘이 같은 브랜드의 다른 지점
(`배다골베이커리하우스`, `배다골베이커리 포레`)이었다. "또 배다골?" 이 되면
목록의 의미가 준다.

상호에서 브랜드를 추측하는 방법도 검토했으나 `베이커리카페 A` / `베이커리카페 B`
처럼 흔한 말이 접두인 경우 서로 다른 카페를 합칠 위험이 있다. **지점은 대개 같은
지역에 모이므로 지역 상한이 더 안전하고, 43개 시군구가 있는데 한 곳에서 3곳을
뽑을 이유도 없다** — 지리적 다양성이 함께 온다.

적용 결과: `배다골베이커리 포레` 가 빠지고 `타임투비`(용인시)가 들어왔다.
후보 자체가 모자랄 때는 상한을 풀어 자리를 채운다 — 빈 자리보다는 낫다.

### 10.1 모바일 우선 설계 (필수 제약)

웹으로 구현하지만 **실제 사용은 100% 모바일**이다. 데스크톱은 개발·관리용
부수 환경으로만 취급한다. 따라서 "반응형"이 아니라 **모바일 전용 설계에
데스크톱을 얹는다.**

| 항목 | 규칙 |
|---|---|
| 기준 뷰포트 | **375~430px 폭에서 설계.** 이 폭에서 완성된 뒤 데스크톱을 본다 |
| 데스크톱 | `max-width: 480px` 센터 정렬. 별도 레이아웃을 만들지 않는다 |
| 네비게이션 | **하단 탭바.** 엄지 도달 범위. 상단 햄버거 메뉴 금지 |
| 카드 | 1열 고정. 2열 그리드 금지 (대형카페 사진은 작으면 의미가 없다) |
| 가로 스크롤 | **금지.** 표를 포함해 body가 가로로 밀리지 않는다 |
| 터치 타겟 | 최소 44x44px. "다녀왔어요" 토글은 56px 이상 |
| 이미지 | 지연 로딩 + 고정 aspect-ratio (레이아웃 시프트 방지) |
| 지도 | **직접 만들지 않는다.** 네이버지도 링크로 넘긴다 (10절) |
| 폰트 | 최소 15px. 딸들은 괜찮지만 79/81년생에게 13px은 작다 |
| PWA | 매니페스트 + 홈 화면 추가. 주소창 없이 앱처럼 열리게 한다 |
| 오프라인 | 마지막 조회 결과를 캐시. 지하철 이동 중에도 목록이 보인다 |

**한 손 엄지로 끝까지 볼 수 있어야 한다.** 이 서비스에서 사용자가 하는
행동은 "스크롤하고 읽기"가 거의 전부다 (3절 ③). 따라서 성능과 가독성이
곧 사용성이며, 카드가 세로로 시원하게 흐르는 것이 최우선이다.
유일한 조작 버튼인 "다녀왔어요" 토글은 화면 하단부에 56px 이상으로 둔다.

### 10.2 카카오톡 주간 알림 — 서비스의 실질적 진입점

**매주 금요일 정오, 카카오톡으로 "심김 빵지순례 · 이번 주" 링크가 온다.**

이것이 이 서비스의 진입점이다. 사용자가 앱을 *여는* 것이 아니라 알림이
*온다*. 앱을 열어야 하는 서비스는 잊히고, 카톡이 오는 서비스는 잊히지 않는다.

#### 전달 경로 — 카카오톡 "나에게 보내기" (메모 API)

카카오톡 메시지 발송 경로를 검토한 결과:

| 경로 | 가능 여부 |
|---|---|
| **나에게 보내기 (메모 API)** | **가능.** 검수 불필요, 발송 제한 없음. 동의항목 설정만 필요 |
| 친구에게 보내기 | 불가. 비즈 앱 등록 + 검수 필요 |
| 알림톡·친구톡 | 불가. 사업자등록 + 비즈니스 채널 필요 |

따라서 **나에게 보내기**가 유일한 현실적 경로다.

#### 2단계 구현 전략

**Phase 1 — 커넥터 활용 (코드 0줄, 계획 1~2 기간에 바로 동작)**

Claude Code에 연결된 카카오 MCP 커넥터(`KakaotalkChat-MemoChat`)를 예약
작업으로 매주 금요일 정오에 호출한다. 파이프라인만 완성되면 **웹앱 없이도
카톡 알림이 먼저 동작한다.**

- 제약: **텍스트 200자**. 이미지 카드(피드 템플릿) 불가
- 제약: 로컬 예약 실행은 PC가 켜져 있어야 한다
- **완화: claude.ai Routine(클라우드 예약)으로 실행하면 PC가 필요 없다.**
  카카오 커넥터는 계정 단위 연결이라 클라우드 실행에서도 붙을 가능성이 높다.
  다만 예약 실행 환경에 커넥터 인증이 없을 수 있어 **보장은 안 된다** —
  파이프라인 완성 후 금요일에 한 번 돌려보면 확인된다 (테스트 비용 거의 0)
- 그럼에도 가치: 알림 문구와 반응을 **웹앱 만들기 전에** 검증할 수 있다

200자 예시 (약 100자로 충분하다):

```
[심김 빵지순례 · 이번 주]

1. 테라로사 서종점 (양평 80분)
2. 카페산 (가평 90분)
3. 더그림 (파주 60분)

자세히 -> https://.../w
```

**Phase 2 — 앱 내장 (계획 3)**

웹앱이 카카오 토큰을 직접 관리해 커넥터 의존을 제거한다.

```
각 구성원이 웹앱에서 "카카오톡 알림 받기" 1회 클릭
   -> 카카오 로그인 (talk_message 동의)
   -> refresh_token 을 kakao_tokens 에 암호화 저장
   -> 매주 금 12:00 배치가 access_token 갱신 후 각자에게 발송
```

- **피드 템플릿** 사용 가능 -> 카페 대표 사진이 담긴 카드로 발송
- refresh_token 유효기간 60일. 주 1회 사용하므로 자동 갱신되어 만료되지 않는다
- 가족 3명은 카카오 개발자 앱의 **팀원으로 초대**해야 동의항목 사용이 가능하다
  (Task 0에서 처리)

#### 폴백 설계

Phase 2의 4인 개별 발송이 정책상 막히면 **아빠 계정 1개로만 발송하고
가족 단톡방에 공유**하는 경로로 축소한다. 웹앱에 카카오톡 공유 버튼을
두어 원탭으로 공유한다.

실은 이 축소판이 더 나을 수도 있다. 단톡방에 뜨면 그 자리에서 대화가
생긴다("여기 어때?"). 개별 알림 4통은 대화를 만들지 않는다.

### 11.1 화제량 수집은 회전식이다 (v3.5)

판정 대기 카페(약 5,100곳)를 **매일** 다시 재고 있었다. 화면에 뜨지 않는
카페의 화제량은 "판정 우선순위" 에만 쓰이므로 매일 잴 이유가 없었다.

| | 회전 전 | 회전 후 |
|---|---|---|
| 카카오 블로그 호출 | 5,875/일 | **1,099/일** |
| Actions 실행 시간 | **18.4분/일** | **4.4분/일** (실측) |

- **추천 대상(active)은 매일 전부** 잰다. 순위와 대표 이미지가 여기서 나오므로
  하루만 낡아도 화면에 그대로 보인다.
- **판정 대기는 가장 오래 안 잰 것부터 하루 800곳.** 약 6~7일에 한 바퀴 돈다.
  판정이 무료 쿼터로 하루 최대 200곳이므로 이보다 자주 잴 필요가 없다.

### 11.2 "결제 없이 계속 돌아간다" 의 근거 (v3.5)

사용자의 전제는 **업데이트도 결제도 없이 평생 자동**이다. 무료 한도를 넘기면
작업이 멈추고, 그 멈춤은 조용하다. 그래서 한도를 명시적으로 기록한다.

| 자원 | 한도 | 실측 사용 | 여유 |
|---|---|---|---|
| GitHub Actions (**비공개** 저장소) | 월 2,000분 | 약 400분 | 5배 |
| 카카오 블로그 검색 | 일 30,000 | 1,099 | 27배 |
| 카카오 길찾기 | 일 10,000 | 신규분만 | 무시 가능 |
| Gemini 무료 티어 | 일일 요청 한도 | 한도까지 쓰고 다음 날 이어감 | — |
| Vercel Hobby | 개인·비상업 | 가족 4명 | 무시 가능 |

**Actions 한도가 유일하게 아슬아슬했다.** 회전 전에는 약 1,400분/월이었다 —
비공개 저장소의 무료 한도가 월 2,000분이므로 재실행 몇 번이면 넘겼다.
저장소를 공개로 바꾸면 무제한이지만, 가족의 별점·후기가 공개되므로 하지 않는다.

**돈이 아니라 부패가 위험이다.** 결제 없이 멈추는 경로는 셋뿐이다.

1. **모델 은퇴** — `gemini-3.1-flash-lite` 가 사라지면 판정이 실패한다.
   감시가 잡고(`source_failing`), 모델 이름 한 줄을 바꾸면 된다.
2. **액션 버전 만료** — v4 액션은 Node 20 기반이었다. 런너가 경고를 내다가
   언젠가 거부한다. v7 / Node 24 로 올렸다 (로컬과 같은 버전).
3. **토큰 만료** — 만료 없는 토큰을 쓴다. 만료를 걸면 그날 수집이 조용히 멈추고
   원인을 찾는 데 시간이 더 든다.

### 11.3 사용량 이상 감시 (v3.5)

사용자가 대화에 노출된 API 키를 **알고서** 교체하지 않기로 했다 (무료 키라
청구 경로가 없고, 실제 피해는 "남이 쿼터를 쓰면 수집이 조용히 멈춘다" 하나).
그 결정을 감시로 받는다.

무료 티어는 사용량 조회 API 가 없으므로 **증상**을 본다.

| 검사 | 수준 | 잡는 것 |
|---|---|---|
| 추천 대상 오늘 측정 < 80% | 경보 | 카카오 수집 고장 |
| 오늘 측정 총량 < 기대치 30% | 경보 | 수집 조기 중단 |
| 대기가 남았는데 오늘 판정 0곳 | 경보 | **키 유출 신호** |
| 소스 연속 실패 3회 이상 | 경보 | 소스 장애 |
| 매일 도는 소스가 36시간 침묵 | 경보 | 크론·워크플로 고장 |
| 쿼터 오류(429) | 경고 | **무료 티어에서는 정상** |
| 오늘 판정 50곳 미만 | 경고 | 쿼터가 일찍 끊김 |

**쿼터 오류 자체는 경보가 아니다.** 하루 한도까지 쓰면 429 는 매일 온다
(실측: classify 가 3곳 처리 후 "일일 쿼터 소진" 으로 중단). 그걸로 매일 메일을
보내면 사흘 뒤부터 아무도 열지 않는다. 키가 새서 남이 쓰는 경우는 "429 가 왔다"
가 아니라 **"한 곳도 못 했다"** 로 드러난다.

알림 경로는 둘이다.

- **GitHub 워크플로 실패 메일** — 경보가 있으면 exit 1. PC 가 꺼져 있어도 닿는다.
- **금요일 정오 카톡 마지막 줄** — `자동수집 정상` / `주의: …` / `점검 필요: …`.
  사용자 요청이며, 핵심은 **없으면 이상한 신호**를 만드는 것이다. 메일은 알림
  자체가 죽으면 조용하지만, 매주 오는 이 줄은 빠지면 눈에 띈다.

**감시에는 API 키를 주지 않는다.** 감시가 키에 의존하면 키가 문제일 때 감시부터
죽는다.

예상 사용량 (설계 시점 추정. 실측은 11.2절):

```
카카오 로컬     그물 A 65x6x3 = 1,170 + 그물 C 정규화 약 500  -> 약 1,700/월
카카오 블로그   화제량 1,099/일 (회전식, 11.1절) + 주차 스니펫(신규만)
Gemini          신규 카페만. 백필 약 5,100건은 하루 200곳씩 나눠 실행
```

**확정 쿼터 (2026-08-20 콘솔 확인):**

| API | 일일 한도 | 예상 사용 | 사용률 |
|---|---|---|---|
| 카카오맵 REST > 키워드로 장소 검색 | 100,000 | 약 2,500/월 | 무시 가능 |
| Daum 검색 > 블로그 검색 | **30,000** | 약 1,500/일 | **5%** |
| 전체 API 월간 | 3,000,000 | 약 48,000/월 | **1.6%** |
| 카카오내비 REST > 자동차 길찾기 | **10,000** | 신규 통과분만 (주 1회) | 무시 가능 |

여유가 매우 크다. 초당 상한과 429 지수 백오프만 지키면 된다.

**이동시간 실측을 도입했다 (2026-08-20 완료).** 8.2절은 실측 경로 API 를
1차 범위에서 제외했으나, 자동차 길찾기가 **일 10,000건 무료**다. 게이트
통과분 298곳을 실측한 결과 근사값의 **평균 절대오차가 9.1분**이었고,
방향까지 계통적으로 갈렸다.

```
과소추정  강화군 +17분  강북구 +12분  강서구 +10분  종로구 +9분
          (다리·도심 도로. 강화 토크라피 36분 -> 실측 60분)
과대추정  이천시 -25분  평택시 -22분  안성시 -22분  가평군 -15분
          (고속도로가 시속 60km 가정보다 빠르다. 여주 카페나드 118분 -> 87분)
```

**이 보정이 추천을 바꿨다.** 파주 과대추정이 풀리면서 더티트렁크가 상위로
올라왔다 — 수도권 대형 베이커리 카페의 대표격이며 정확히 우리가 찾던 종류다.

카페는 움직이지 않으므로 한 번 재면 끝이다. `npm run drive` 는 이미 값이
있으면 건너뛰므로 매주 돌려도 신규분만 호출한다. 실측 실패는 근사값으로
폴백하며 카페를 목록에서 떨어뜨리지 않는다.

Gemini 무료 티어의 일일 요청 한도에 걸릴 수 있으므로 초기 백필은 며칠에
걸쳐 나누어 돌리는 것을 전제로 설계한다 (일회성 작업이므로 수용 가능).

### 11.5 판정 순서 — 화제량만 보면 집 근처가 영원히 밀린다 (v3.7)

가족 의견에서 시작했다: **"송도와 영종도 카페가 너무 없다."**

카페가 없는 것이 아니었다. 수집은 했는데 **판정을 못 했다.**

```
송도    75곳 수집 -> 판정 완료 10곳 (대기 59)
영종    92곳 수집 -> 판정 완료  7곳 (대기 76)
연수구 117곳 수집 -> 판정 완료 14곳
```

원인은 판정 순서다. `postsPer30` 내림차순으로 하루 200곳을 처리하는데:

```
인천 대기분 화제량 중앙값  1.0
그날의 판정 컷            8.1     <- 컷을 넘는 인천 카페는 24곳뿐
```

**블로그 글은 멀리 나들이 간 곳에 쓰인다.** 집에서 25분 거리 카페는 글감이
되지 않으니 화제량이 낮고, 화제량 순 줄에서 영원히 뒤로 밀린다. 그런데
가족이 실제로 가장 자주 가는 곳이 거기다. 지표와 목적이 어긋난 것이다.

거리 감쇠를 곱하는 방법(`화제량 x e^(-분/70)`)도 검토했는데 부족하다 —
송도 25분은 0.70, 양평 90분은 0.28 로 2.5배 차이인데 화제량은 8배 차이다.
곱셈으로는 뒤집히지 않는다.

그래서 **몫을 떼어 준다.** 하루 처리량의 30% 를 거리순으로 채운다. 화제량
순의 원래 목적(첫날부터 추천 상단이 채워지고 지역이 섞인다)은 나머지 70% 가
그대로 지킨다.

`--order near` 로 특정 지역을 몰아서 메울 수도 있다. 이번처럼 이미 쌓인
적체를 한 번에 푸는 용도다.

### 11.6 화제량 컷은 거리에 따라 달라야 한다 (v3.7)

11.5 에서 판정 **순서**를 고쳤는데, 돌려 보니 통과 18곳 / 배제 219곳이었다.
순서를 앞당겨도 컷에서 잘려 나갔다. 진짜 원인은 컷이었다.

```
화제량 부족으로 배제된 179곳 중 123곳(69%)이 40분 이내
```

절대값 하나(월 8건)로 자르면 **집 근처가 집중적으로 잘린다.** 블로그 글은
멀리 나들이 간 곳에 쓰이기 때문이다. 부평구 2분 거리 `빵고베이커리` 는
월 5.5건으로 탈락했다.

월 8건이 실제로 묻고 있던 것은 **"한 시간 넘게 운전할 만큼 뜨거운가"** 다.
25분 거리에는 그만한 근거를 요구할 이유가 없다.

| 이동시간 | 컷 |
|---|---|
| 40분 이내 | 월 4건 |
| 41~70분 | 월 6건 |
| 71분 이상 | 월 8건 |
| 미상 | 월 8건 (가장 엄하게) |

경계값은 스펙의 거리 감쇠 기준을 따른다 — 70분이 e^-1 지점이고, 40분은
"가볍게 다녀오는" 거리다.

**품질은 뒤쪽 게이트가 지킨다.** 동네 카페 판별은 화제량이 아니라 성격 태그
0개가 한다 (7절). 이 컷의 실질 역할은 LLM 호출 비용 절약이다. 실제로 컷을
낮춘 뒤 골든셋 기준선이 그대로였다 — 오통과율 5%, 경계 통과율 50%.

곱셈(`화제량 x e^(-분/70)`)도 검토했는데 부족했다. 25분은 0.70, 90분은 0.28
로 2.5배 차이인데 화제량은 8배 차이라 뒤집히지 않는다. 컷 자체를 나눠야 했다.

**이미 배제된 것은 자동으로 돌아오지 않는다.** `excluded_auto` 로 굳기
때문이다. 그래서 `npm run requeue` 를 만들었다 — 화제량 사유로 배제된 것 중
지금 규칙이면 통과할 것을 대기로 되돌린다. 정밀도·프랜차이즈·업종 사유는
규칙이 안 바뀌었으므로 손대지 않는다.

### 11.7 지점명이 붙은 카페가 구조적으로 불리했다 (v3.7)

가족 질문에서 시작했다: **"포레스트아웃팅스 일산점·송도점이 왜 없나?
용인점은 나오는데."**

관련성 판정(`isRelevant`)이 **상호명 전체**를 요구했다. 그런데 블로거는
`포레스트아웃팅스 일산본점` 이라고 쓰지 않는다 — `일산 포레스트아웃팅스`,
`포레스트아웃팅스 본점` 이라고 쓴다. 실측 (받은 글 50건 기준):

```
상호 전체 요구        4건 -> 정밀도  8%  -> 탈락
기본상호 "포레스트아웃팅스" 만  46건 -> 브랜드 전체 글이 모든 지점에 중복
기본상호 + 지점 힌트    11건 -> 통과
```

용인점만 살아남은 것은 우연이다. `포레스트아웃팅스 용인점` 이라는 정확한
표기를 쓴 글이 마침 많았다.

**기본 상호와 지점 힌트를 둘 다 요구한다** (`splitBranch`). 지점 힌트가
있어야 용인점 글이 송도점에 잡히지 않는다 — 기본 상호만 보면 화제량이
브랜드 전체로 부풀려진다.

접미사 분리는 공백을 요구한다. 없이 붙여 쓰면 `카페만점` 이 `카페` + `만`
으로 갈라진다. 지점 힌트가 한 글자여도 지점으로 보지 않는다.

효과 (실측):

```
포레스트아웃팅스 일산본점  정밀도 10% -> 84%  · 월 12건 -> 73건
포레스트아웃팅스 송도점    정밀도 34% -> 80%  · 월 2.4건 -> 64건
포레스트아웃팅스 용인점    정밀도 66% -> 94%  (통과분도 개선)
지점 카페 470곳이 정밀도 컷을 새로 넘었다
```

골든셋 기준선은 그대로다 — 오통과율 5%, 경계 통과율 50%.

**되돌리기의 함정.** 이미 배제된 것은 `excluded_auto` 로 굳어 자동으로
돌아오지 않아 `requeue` 로 되살린다. 여기서 한 번 틀렸다 — 화제량 사유
배제분을 **저장된 값으로** 판단했더니 송도점이 걸러졌다 (옛 값 월 2.4건 →
"지금도 탈락"). 규칙이 바뀌면 값 자체가 달라지므로, **지점 카페는 조건 없이
줄에 세우고 다시 재게** 해야 한다.

### 11.4 이번 주 추천은 다음 것이 나올 때까지 유효하다 (v3.7)

`week` 를 `s.weekOf === weekOf` 로 정확히 맞춰 골랐다. 그래서 **월요일
09시(KST)부터 목요일 밤까지 사흘 동안 추천이 사라졌다.**

```
목 19:47 UTC   후보 확정. 그 주 월요일 날짜가 weekOf 로 붙는다
금 정오        카카오톡 발송
월 09:00 KST   weekOf 가 다음 주로 넘어간다  ->  일치하는 후보 없음  ->  week: []
```

화면이 통째로 비지는 않았다 — 종합점수 순으로 대체된다. 하지만 그것은 지역
다양성과 주차 등급을 지키며 고른 열 곳이 아니다. 실측으로 2026-08-24 에
`week: []` 를 확인했다.

고친 방식은 **가장 최근 것으로 내려오기**다 (`pickWeek`). 미래 `weekOf` 는
쓰지 않는다 — 수동 실행으로 앞선 후보가 들어와도 앞당겨 보여주지 않는다.

## 12. 에러 처리 — 우아한 저하

| 상황 | 처리 |
|---|---|
| 소스 어댑터 실패 | `source_health` 기록, 나머지 소스로 계속 진행 |
| 화제량 재수집 실패 | 직전 스냅샷 유지, "N일 전 데이터" 표시 |
| LLM 추출 실패 | 3회 재시도 후 `pending_extraction` 큐에 남김 |
| LLM 스키마 위반 | 구조화 출력 재시도. 3회 실패 시 사람 검수 큐 |
| 카카오 조회 0건 | 상호명 정규화 후 1회 재시도, 실패 시 스킵 |
| 배치 전체 실패 | 웹은 마지막 성공 데이터로 정상 동작 |

**어떤 실패도 서비스를 멈추지 않는다.** 관리 화면의 배지로만 드러난다.

| 스코어 공식 | 골든 케이스 단위 테스트. 경계값(가속도 1.0, 0건, 신규오픈) |
| 태그 판정 | 규칙 단위 테스트. 소형 임계 상향 케이스 포함 |
| 하드 배제 | 프랜차이즈·카테고리·지점접미사 각각 |
| 소스 어댑터 | `raw_snapshots` 실물을 fixture로 재생. **실제 API 미호출** |
| LLM 추출 품질 | **골든셋 40곳**. 시스템이 후보를 뽑고 사람이 O/X 판정 |

### 13.1 골든셋 구축 — 층화 추출 + CLI O/X 판정

**골든셋이 이 프로젝트의 품질 기준선이다.** 다만 사람이 카페를 떠올려
목록을 만드는 방식은 부담이 크고, 떠올린 곳만 들어가서 표본이 편향된다.
그래서 방향을 뒤집는다. **시스템이 후보를 뽑고 사람은 O/X만 누른다.**

#### 후보 추출 — 반드시 층화 추출로

파이프라인을 1회 돌린 뒤 **점수 구간별로 골고루** 뽑는다. 상위권만
뽑으면 정작 판정이 흔들리는 구간을 측정하지 못한다.

| 구간 | 수 | 측정 목적 |
|---|---|---|
| 상위 (FinalScore 상위 20%) | 10곳 | 추천 최상단의 신뢰도 |
| 중간대 | 10곳 | 일반적 판정 품질 |
| **컷라인 근처 (경계)** | 10곳 | **컷 위치가 맞는지 — 가장 중요** |
| 자동 탈락 처리된 곳 | 10곳 | 오탈락(억울한 탈락) 검출 |

총 40곳. 곳당 약 10초, 전체 **7분 내외**를 목표로 한다.

#### 판정은 CLI에서 한다 (웹 화면을 만들지 않는다)

```
npm run label
```

초기 1회 집중 작업이고 아빠만 쓴다. 웹 UI를 만들면 화면·라우팅·상태관리가
붙는데 얻는 것이 없다. 터미널 한 줄이면 된다.

```
[12/40]  경계 구간

  테라로사 서종점                        양평군
  좌석 ~250   주차 A   메뉴 Lv2
  태그  대형카페 · 대형베이커리 · 뷰맛집 · 정원마당형
  근거  "2층 통창에 좌석 200석 넘고 주차장도 넓어요"
  주차  "전용 주차장 50대 이상, 주말에도 여유"

  네이버  https://map.naver.com/p/search/양평군%20테라로사%20서종점

  [o] 나왔으면 좋겠다   [x] 안 갈 곳   [?] 모름   [q] 중단
>
```

`?` 를 반드시 제공한다. 모르는 곳에 억지로 답하게 하면 라벨이 오염된다.
`?` 는 라벨에서 제외한다. 판단이 안 서면 링크를 눌러 네이버지도에서 확인한다.
`q` 로 중단해도 진행 상황이 `golden_labels` 에 저장되어 이어서 할 수 있다.

#### X 이유 태그

`x` 를 누르면 이유를 한 번 더 묻는다. 이것이 **어느 Layer가 틀렸는지
진단**한다. 없으면 정확도 숫자만 알고 무엇을 고쳐야 할지는 모른다.

```
  왜 아닌가?
  [1] 동네 카페다   [2] 주차가 안 된다   [3] 너무 작다
  [4] 너무 멀다     [5] 그냥 취향이 아니다
```

| 이유 | 고쳐야 할 곳 |
|---|---|
| 동네 카페다 | Layer 2 화제량 컷 / Layer 4 태그 임계 |
| 주차가 안 된다 | Layer 4c 주차 등급 판정 |
| 너무 작다 | `scale` · `seats_estimate` 추출 |
| 너무 멀다 | `distance_decay` 계수 |
| 그냥 취향이 아니다 | 알고리즘 문제 아님. 무시한다 |

#### 측정 항목

`npm run label -- --report` 로 출력한다.

- **동네카페 오통과율** — 상위·중간 구간에서 `x` 비율. **체감 품질을 결정하는 값**
- **오탈락률** — 탈락 구간에서 `o` 비율. 좋은 곳을 버리고 있는지
- **경계 구간 o:x 비율** — 5:5에 가까우면 컷 위치가 적절하다. 한쪽으로
  치우치면 컷라인을 옮긴다
- x 이유 분포 — 다음에 고칠 Layer의 우선순위

프롬프트나 스코어 공식을 수정할 때마다 이 골든셋으로 회귀 테스트한다.

## 15. 성공 기준

1. 아내분이 **인스타 대신 금요일 카톡 링크를 먼저 연다**
2. 리스트 상위 20곳에 동네 카페가 **1곳 이하** (13.1절 오통과율로 측정)
3. 주말 후보 **첫 10곳 중 최소 1곳은 실제로 가고 싶은 곳** (못 고르면 다음 10곳)
4. 주차 때문에 헛걸음한 적이 **0회**
5. **3개월간 유지보수 개입 없이** 배치가 돌아간다

4번과 5번이 v2에서 새로 들어왔다. v1의 "딸들이 투표에 자발적으로 참여한다"는
투표 기능 제거로 삭제되었다 — 결정은 가족 단톡방에서 한다 (3절 ④).
